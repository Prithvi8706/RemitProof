## 1. Objective and rationale

A payment resolves only if both hold:

1. The proposal passes the proof and sufficiency checks, as today.
2. Exactly one financially valid allocation is authorizable, and the proposal names it.

An allocation is authorizable when the same proof and sufficiency checks pass for it with its canonical citations (DD-10).

Why: finding F4. Evidence is judged relative to the proposed customer. When two customers share a known payer and each customer's mailbox says "apply this payment to our invoice", a proposal for either one resolves today. The answer then depends on which one the model happened to propose. After this task both allocations are found authorizable, and the payment goes to review with reason `multiple_authorizable_allocations`.

Condition 2 is added on top of condition 1. Nothing that is refused today becomes resolvable. This is the conservative form of DD-09.

## 3. Current behaviour and references

`backend/app/services/verifier_only.py` (created by RP-003) contains `canonical_proposal(bundle, alternative)` and, inside `verifier_only_decision`, a loop that builds the canonical proposal for every alternative, runs `verify_candidate` and `evaluate_evidence_sufficiency`, and keeps the alternatives whose result has `safe_to_resolve` true. That loop is the definition of "authorizable". It lives in an evaluation module that the runtime must not import (`test_runtime_modules_do_not_import_the_baseline`).

This task moves `canonical_proposal` and the loop into a runtime module, `authorization.py`. `verifier_only.py` imports them from there. The import boundary test stays valid without change: the pipeline imports `authorization`, never `verifier_only`.

In `process_payment`, after RP-104, the proposal path computes `proof`, `alternatives = list(outcome.alternatives)` and `sufficiency`, then builds `conflict`, `counterfactuals` and `decision_artifact` from them, then decides on `sufficiency.safe_to_resolve`.

## 6. Input and output contracts

### 6.1 `canonical_proposal`

Moved without change from `verifier_only.py`. Citations in order, without duplicates: the alternative's customer ID, its credit IDs sorted ascending, then the IDs of the bundle's emails whose `customer_id` equals the alternative's customer, in bundle order.

### 6.2 `authorizable_allocations`

For each alternative, in the given order: build the canonical proposal, `proof = verify_candidate(bundle, proposal)`, `sufficiency = evaluate_evidence_sufficiency(bundle, proposal, proof, list(alternatives))`. Keep `(alternative, proposal)` when `sufficiency.safe_to_resolve` is true. Return the kept pairs in order.

### 6.3 `names_allocation`

True when `proposal.proposed_customer == alternative.customer_id` and the sets of invoice IDs are equal and the sets of credit IDs are equal.

### 6.4 `authorization_block_reason`

| `authorizable` | Result |
| --- | --- |
| Two or more pairs | `"multiple_authorizable_allocations"` |
| Exactly one pair, and the proposal names its allocation | `None` |
| Exactly one pair, and the proposal names something else | `"proposal_not_authorizable"` |
| Empty | `"proposal_not_authorizable"` |

### 6.5 `process_payment`

Directly after `sufficiency = evaluate_evidence_sufficiency(...)` and before `conflict = build_conflict(...)`:

```
if sufficiency.safe_to_resolve:
    block_reason = authorization_block_reason(
        proposal,
        authorizable_allocations(proof_bundle, alternatives),
    )
    if block_reason is not None:
        sufficiency = sufficiency.model_copy(
            update={"safe_to_resolve": False, "abstention_reason": block_reason}
        )
```

Nothing after this block changes. Because the block replaces `sufficiency` before the conflict, the counterfactuals, the decision artifact and the decision are built, a blocked payment is reported consistently: `decision.decision == "human_review"`, `decision.reason == block_reason`, `sufficiency.safe_to_resolve is False`, `resolution_proof is None`, `blocked_decision` set.

Authorization is computed only when the proposal already passes. A proposal that fails keeps its existing reason.

## 9. Edge cases and error handling

| Case | Required behaviour |
| --- | --- |
| Proposal passes; the single authorizable allocation is the proposed one | Resolved, as before |
| Proposal passes; two allocations are authorizable | Review, `multiple_authorizable_allocations` |
| Proposal passes with its own citations; nothing is authorizable with canonical citations | Review, `proposal_not_authorizable` |
| Proposal fails | Existing reason. `authorizable_allocations` is not called. |
| Rules-only matched path, status gate, earlier gates | Unchanged. This task touches only the proposal path. |

Predicted behaviour change, outside the legacy corpus only: resolutions become reviews in the situations of rows 2 and 3 of section 9.

Stated limit: `VerifierOnlyInvestigator` receives the prompt bundle and enumerates over it, while the runtime authorizes over the proof bundle. The two agree on every legacy payment (test 11). On a ledger where the cap hides the only authorizable allocation, the baseline proposes nothing and the runtime could accept a correct proposal from elsewhere. This makes the baseline conservative, not unsound. It is recorded in `ARCHITECTURE.md`.
