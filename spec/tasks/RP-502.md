## 1. Objective and rationale

Add `solve(problem)`: a depth-first search over a `Problem` (RP-501) that returns every allocation whose net equals the target, and the number of search nodes it visited.

Why: the existing enumerator tries every invoice subset, so its cost doubles with each invoice (597 ms at 16 invoices, 10.4 s at 20, `AUDIT_VALIDATION.md` section 2). A search that abandons a branch as soon as the target is out of reach visits far fewer. In the dry run, 840 synthetic 16-invoice ledgers (the three shapes of RP-508) needed at most 32,983 nodes and 10 ms each.

The plan had this task "without credits" and a separate task for credit options. The dry run showed there is nothing to separate: RP-501 already turns each invoice and each fitting set of its credits into one option with a net between zero and the invoice amount, and the search treats one option and several options with the same three lines. Credits are therefore covered here. RP-503 is reused for the solution limit.

This task has no limit and no budget: `solve` always runs to the end. RP-503 and RP-504 add the two ways to stop early. Nothing consumes the solver yet. No decision changes.

## 6. Input and output contracts

### 6.1 `solve(problem)`

| Input | Result |
| --- | --- |
| `problem.groups` is empty (any target) | `SolveResult(status="complete", solutions=(), nodes=0)` |
| `problem.groups` is not empty and `problem.target < 1` | `ValueError("target must be at least 1")` |
| Otherwise | `status="complete"`; `solutions` holds every allocation whose net equals `problem.target`, each exactly once; `nodes` is the number of nodes visited (section 8) |

A solution is `(customer_id, invoice_ids, credit_ids)`:

- `invoice_ids`: the IDs of the items taken, as a tuple, ascending.
- `credit_ids`: the credit IDs of all taken options together, as a tuple, ascending.

`solutions` is sorted ascending (ordinary tuple comparison). Because groups are disjoint by customer and options of one item have distinct credit sets, no solution can occur twice. The function does not de-duplicate.

`solve` trusts the `Problem`. It does not re-check the three guarantees of section 3. Callers build problems with `build_problem` only. Tests build small problems by hand and keep the guarantees.

## 8. Algorithm

### 8.1 The search

Groups are searched one after another, in the order they have in the problem. For one group with items `items[0]` to `items[n-1]`:

```
reach[n] = 0
reach[i] = reach[i + 1] + items[i].amount          for i = n-1 down to 0

visit(i, net):
    nodes += 1
    if net > target: return                          # bound 1, overshoot
    if net + reach[i] < target: return               # bound 2, undershoot
    if i == n:
        record (customer, sorted IDs of the taken items, sorted credit IDs of the taken options)
        return
    for option in items[i].options, in their order:
        take items[i] with this option; visit(i + 1, net + option.net); undo
    visit(i + 1, net)                                # skip items[i]

visit(0, 0)
```

`nodes` is one counter for the whole call, across groups. A node is one call of `visit`, counted before either bound is checked. The count is part of the result and is pinned by tests, so the order above (options first, in order, then skip) is not free to change.

### 8.2 Why the search is complete without the bounds

Remove the two bound lines. Then `visit` tries, for every item, each of its options and "skip". Every way of deciding all items is reached exactly once, at `i == n`. An allocation is exactly such a way with at least one item taken. So the unpruned search sees every candidate allocation once.

### 8.3 Bound 1, overshoot: `net > target`

Claim: below a node with `net > target` there is no allocation that nets to the target.

Derivation. Going down one level adds either an option's net or, on skip, nothing. RP-501 guarantees every option's net is zero or more. So along any path the running net never falls. If it is already above the target, it stays above the target to the end of the path.

Why the comparison is strict. At `net == target` the allocation may already be complete (skip everything else), so that node must go on.

Where a naive version goes wrong. If credits were separate steps with negative value, the running net could fall again and this bound would be false. Take invoice `INV_B` of 1200.00 with credit `CR_1` of 200.00, invoice `INV_A` of 1000.00, and a payment of 1000.00. After taking `INV_B` the net is 1200.00. A search with negative credit steps and this bound would cut there and lose `INV_B` with `CR_1`. Here `INV_B` with `CR_1` is one option of net 1000.00, so the net never passes through 1200.00 on that path. Test 5 is this ledger.

### 8.4 Bound 2, undershoot: `net + reach[i] < target`

Claim: below a node at position `i` with `net + reach[i] < target` there is no allocation that nets to the target.

Derivation. From position `i` on, each item adds at most its full amount: RP-501 guarantees every option's net is at most the invoice amount, and skipping adds zero. So the most the remaining items can add together is `reach[i]`, the sum of their amounts. If even that does not lift the net to the target, nothing below does.

Why the comparison is strict. At `net + reach[i] == target` taking every remaining item in full hits the target exactly, so that node must go on.

Where a naive version goes wrong. Building `reach` from each item's smallest net (the invoice minus all its credits) understates what the item can add and cuts branches that hold allocations. Building it from the last option, or from the option list's first element after re-sorting by net, has the same fault. `reach` uses `item.amount`, nothing else. In the dry run this defect passed every hand-written case and was caught only by the two differential tests (tests 11 and 14). That is why they exist.

### 8.5 Why no comparison is needed at the end

At `i == n`, `reach[n]` is 0. A node that passed bound 1 has `net <= target`. A node that passed bound 2 has `net + 0 >= target`. So `net == target`. And because `target >= 1` while skipping everything gives net 0, at least one item was taken. Every node that reaches the `i == n` line is an allocation, and by 8.2 to 8.4 every allocation reaches it.

### 8.6 Worked example

One group, four items in this order, each with one option: `INV_A` 700, `INV_B` 500, `INV_C` 300, `INV_D` 200 (minor units). Target 1000.

`reach = [1700, 1000, 500, 200, 0]`.

| Node | Position | Taken so far | Net | Check | Outcome |
| --- | --- | --- | --- | --- | --- |
| 1 | 0 | none | 0 | 0 + 1700 >= 1000 | Go on. Take `INV_A`. |
| 2 | 1 | A | 700 | 700 + 1000 >= 1000 | Go on. Take `INV_B`. |
| 3 | 2 | A, B | 1200 | 1200 > 1000 | Cut by bound 1. Back to node 2, skip `INV_B`. |
| 4 | 2 | A | 700 | 700 + 500 >= 1000 | Go on. Take `INV_C`. |
| 5 | 3 | A, C | 1000 | 1000 + 200 >= 1000 | Go on. Take `INV_D`. |
| 6 | 4 | A, C, D | 1200 | 1200 > 1000 | Cut by bound 1. Back to node 5, skip `INV_D`. |
| 7 | 4 | A, C | 1000 | End of the list | Allocation: `INV_A`, `INV_C`. Back to node 4, skip `INV_C`. |
| 8 | 3 | A | 700 | 700 + 200 < 1000 | Cut by bound 2. Back to node 1, skip `INV_A`. |
| 9 | 1 | none | 0 | 0 + 1000 >= 1000 | Go on (equality). Take `INV_B`. |
| 10 | 2 | B | 500 | 500 + 500 >= 1000 | Go on (equality). Take `INV_C`. |
| 11 | 3 | B, C | 800 | 800 + 200 >= 1000 | Go on (equality). Take `INV_D`. |
| 12 | 4 | B, C, D | 1000 | End of the list | Allocation: `INV_B`, `INV_C`, `INV_D`. Back to node 11, skip `INV_D`. |
| 13 | 4 | B, C | 800 | 800 + 0 < 1000 | Cut by bound 2. Back to node 10, skip `INV_C`. |
| 14 | 3 | B | 500 | 500 + 200 < 1000 | Cut by bound 2. Back to node 9, skip `INV_B`. |
| 15 | 2 | none | 0 | 0 + 500 < 1000 | Cut by bound 2. Done. |

15 nodes, 2 allocations. Without the bounds the same search visits 31 nodes. Test 1 asserts exactly this result, with `nodes=15`.

Nodes 9, 10 and 11 pass bound 2 on equality. A bound written with "at most" in place of "below" would cut node 9 and lose the second allocation. Node 7 is reached through node 5, where the net already equals the target. A bound 1 written with "at least" in place of "above" would cut node 5 and lose the first.

### 8.7 Cost

Worst case exponential in the number of items: the problem is subset sum. Measured in the dry run on the legacy corpus: 1,943 nodes for all 80 payments together. Eight equal amounts with a target of four of them: 363 nodes, 70 allocations. Larger ledgers are measured in RP-508.

## 9. Edge cases and error handling

| Case | Required behaviour |
| --- | --- |
| Target above the sum of all amounts of a group | That group ends after 1 node |
| Target equal to the sum of all amounts | One allocation: every item with its first option |
| Target below the smallest amount, no option with a smaller net | No allocation |
| An item with an option of net 0 | It can join any allocation. Both the allocation without it and the one with it are returned. |
| Amounts 1000.01, 1000.00 and 999.99 | Told apart exactly. No tolerance anywhere. |
| Two groups that each reach the target | Both allocations, never a combination across groups |
| Recursion depth | One level per item. RP-507 limits a group to 64 items. No change to the interpreter's recursion limit. |

### 12.1 `_drawn_problem(seed)`

`amounts = (100, 200, 300, 400, 500, 700, 1000)`.

1. Number of groups: `_draw(f"{seed}:groups", 1, 2)`. Group `g` (from 0) has customer ID `f"CUS_{g + 1}"`.
2. Number of items in group `g`: `_draw(f"{seed}:{g}:items", 1, 7)`.
3. For item `i` (from 0) with `key = f"{seed}:{g}:{i}"`: `amount = amounts[_draw(f"{key}:amount", 0, 6)]`. Number of credit options: `_draw(f"{key}:options", 0, 2)`. Credit option `o` (from 0): `net = _draw(f"{key}:{o}:net", 0, amount // 100) * 100`, `credit_ids = (f"CR_{g}{i}{o}",)`. The item is `_item(f"INV_{g}{i}", amount, *credit_options)`.
4. Sort each group's items by amount descending, then invoice ID.
5. `target = _draw(f"{seed}:target", 1, 25) * 100`.

The drawn nets include 0 and the full amount, so both ends of the option guarantee are exercised.
