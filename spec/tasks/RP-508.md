## 1. Objective and rationale

Measure, on synthetic ledgers, what the search of RP-507 does as a customer's ledger grows from 8 to 64 open invoices, and commit the result as a table that a fresh run reproduces byte for byte.

The table reports outcomes and node counts. Both are the same on every machine and every Python version, because the node budget counts nodes and every random draw is a SHA-256 of a key string. Wall-clock time is machine dependent. It is printed on request and never written to a file.

What the dry run measured, so that the reader knows what to expect:

| Invoices | Ledgers | Answered | Unknown: node budget | Unknown: allocation limit |
| --- | --- | --- | --- | --- |
| 8 | 360 | 360 | 0 | 0 |
| 16 | 360 | 360 | 0 | 0 |
| 32 | 360 | 239 | 66 | 55 |
| 64 | 360 | 119 | 137 | 104 |

Read it plainly. Up to 16 invoices the search always finishes. At 64 invoices it answers one ledger in three, mostly payments that cover one or two invoices. Every unanswered ledger goes to human review, so nothing here is unsafe. But "the limit is 64" must not be reported as "ledgers of 64 are solved". This table is the evidence for the honest sentence.

Every ledger is synthetic. No real ledger of 32 or 64 open invoices exists in this project. The table says nothing about how often real customers have such ledgers, and the generated Markdown says so in its first paragraph.

The plan had this task at 2 hours. It is 3: the table is reproducible and pinned, which the scope statement did not ask for.

## 6. Input and output contracts

### 6.1 Draws

`draw(key, low, high)` is `low + int(hashlib.sha256(key.encode("utf-8")).hexdigest(), 16) % (high - low + 1)`.

`amounts_for` returns invoice amounts in minor units:

| Shape | Amount of the invoice at position `index` |
| --- | --- |
| `distinct` | `draw(f"distinct:{instance}:{index}", 5000, 2000000)` |
| `priced` | `2500 * draw(f"priced:{instance}:{index}", 1, 200)` |
| `recurring` | `draw(f"recurring:{instance}:base", 5000, 2000000)` when `index` is even, else `draw(f"recurring:{instance}:{index}", 5000, 2000000)` |

Any other shape raises `ValueError(f"unknown shape {shape}")`.

`paid_indices` sorts `range(invoices)` by `hashlib.sha256(f"paid:{instance}:{invoices}:{paid}:{index}".encode("utf-8")).hexdigest()`, keeps the first `paid` positions and returns them in ascending order.

### 6.2 `ledger`

One customer and no credits or emails:

| Record | Fields |
| --- | --- |
| Payment | `payment_id="PAY_1"`, `date=date(2026, 8, 10)`, `currency="USD"`, `payer_name="Acme Trading Ltd"`, `bank_reference="BNK-1"`. The amount is the sum of the amounts at `paid_indices(invoices, paid, instance)`. |
| Customer | `customer_id="CUS_1"`, `legal_name="Acme Trading Ltd"` |
| Invoice at position `index` | `invoice_id=f"INV_{index:03d}"`, `customer_id="CUS_1"`, `currency="USD"`, `issue_date=date(2026, 6, 16)`, `due_date=date(2026, 7, 16)`, `description="Services"`, the amount of 6.1 |

Minor units become a `Decimal` as `Decimal(f"{minor // 100}.{minor % 100:02d}")`. The function returns `ProofSet(prompt_bundle=bundle, proof_bundle=bundle, complete=True, incomplete_reasons=())` with one bundle used for both views.

So every ledger has at least one allocation by construction, and the outcome `none` cannot occur.

### 6.3 `measure`

Calls `solve(build_problem(proof_set.proof_bundle, CREDITS_PER_INVOICE_LIMIT), solution_limit=ALTERNATIVE_LIMIT + 1, node_budget=NODE_BUDGET)` with the constants of `app.services.search`. Returns `(outcome, result.nodes)`:

| Solver status | Outcome |
| --- | --- |
| `node_budget` | `"node_budget"` |
| `solution_limit` | `"alternative_limit"` |
| `complete` with 0, 1, more solutions | `"none"`, `"unique"`, `"ambiguous"` |

### 6.4 `cell`

Runs `measure(ledger(shape, invoices, paid, instance))` for `instance` in `range(instances)`. Returns a dict with these keys in this order: `shape`, `invoices`, `paid`, `instances`, then one count per name in `OUTCOMES`, then `median_nodes` and `max_nodes`. With the node counts sorted ascending as `nodes`, `median_nodes` is `nodes[len(nodes) // 2]` and `max_nodes` is `nodes[-1]`.

### 6.5 `build_report`

For each size: if it is below `max(PAID)` or above `INVOICE_SEARCH_LIMIT`, raise `ValueError(f"size {size} is outside {max(PAID)} to {INVOICE_SEARCH_LIMIT}")`.

`cells` is `cell(shape, size, paid, instances)` for `shape` in `SHAPES`, then `size` in `sizes`, then `paid` in `PAID`.

`by_size` has one dict per size, in order: `invoices`, `ledgers` (sum of `instances` over that size's cells), `answered` (sum of `unique`, `ambiguous` and `none`), `node_budget`, `alternative_limit`.

The report:

| Key | Value |
| --- | --- |
| `format_version` | `1` |
| `synthetic` | `True` |
| `constants` | `invoice_search_limit`, `credits_per_invoice_limit`, `alternative_limit`, `node_budget`, read from `app.services.search` |
| `shapes` | The three notes of 6.6 by shape name |
| `sizes` | The sizes as a list |
| `paid` | `[1, 2, 3, 4, 6, 8]` |
| `instances_per_cell` | `instances` |
| `by_size` | As above |
| `cells` | As above |

No key holds a time, a date, a host name or a Python version.

`report_bytes(report)` is `json.dumps(report, indent=2, sort_keys=True)` plus one newline, encoded as UTF-8.

### 6.6 `markdown_bytes`

Lines joined with `"\n"`, plus one final newline, encoded as UTF-8. The lines, in order. `<...>` marks a value taken from the report.

```
# Solver scaling on synthetic ledgers

Generated by `backend/scripts/solver_scaling.py --write`. Do not edit by hand.

Every ledger here is synthetic: one customer, no credits, and a payment that equals a drawn set of its
invoices. No real ledger of this size exists in the project. The table says how the search behaves as a
ledger grows. It says nothing about how often real customers have such ledgers.

Limits in force: <invoice_search_limit> eligible invoices per customer, <alternative_limit> allocations, <node_budget> search nodes.

| Shape | Meaning |
| --- | --- |
| `distinct` | every amount drawn to the cent between 50.00 and 20000.00 |
| `priced` | every amount a multiple of 25.00 between 25.00 and 5000.00 |
| `recurring` | every second invoice repeats one amount; the others are drawn as in distinct |

## By ledger size

| Invoices | Ledgers | Answered | Unknown: node budget | Unknown: allocation limit |
| --- | --- | --- | --- | --- |
| <invoices> | <ledgers> | <answered> | <node_budget> | <alternative_limit> |

Answered means the search returned `unique`, `ambiguous` or `none`. Unknown goes to human review.

## By cell

<instances_per_cell> ledgers per row. Paid is the number of invoices the payment covers.

| Shape | Invoices | Paid | Unique | Ambiguous | None | Node budget | Allocation limit | Median nodes | Max nodes |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| `<shape>` | <invoices> | <paid> | <unique> | <ambiguous> | <none> | <node_budget> | <alternative_limit> | <median_nodes> | <max_nodes> |
```

The "By ledger size" row repeats once per entry of `by_size`, and the "By cell" row once per cell. The three meanings in the shape table are the `shapes` notes of the report, word for word.

### 6.7 `print_timings`

Prints `Wall-clock seconds on this machine. Not written to any file.`, then the header `invoices  ledgers  search_total_s  search_worst_s  enumerator_total_s`, then one line per size. For every ledger of that size (all shapes, all `PAID`, `instances` each) it times one call of `search` with `time.perf_counter`. For sizes of at most 16 it also times `find_valid_alternatives` on the proof bundle. The last column is that total with three decimals, or `not run` above 16. Nothing is written to disk.

### 6.8 `main`

| --- | --- | --- |
| `--timings` | `print_timings(sizes, instances)` | 0 |
| `--write`, a target file exists, no `--force` | Prints `refusing to overwrite <first existing path>; pass --force after review`. Writes nothing. | 2 |
| `--write` otherwise | Writes both files with `atomic_write_bytes`, the JSON first. Prints `wrote <path>` for each. | 0 |
| `--check`, a file is missing | Prints `table is missing: <path>` | 2 |
| `--check`, a file differs from a fresh run after CRLF is normalized to LF | Prints `table differs from a fresh run: <path>` | 1 |
| `--check`, both equal | Prints `tables match a fresh run: <out-dir>` | 0 |

Paths are printed as resolved absolute paths. The JSON file is checked before the Markdown file.

## 8. Algorithm

No algorithm beyond section 6. The cost of a full run is dominated by the ledgers that run out of budget: 203 of them at about a third of a second each.

Wall-clock times seen in the dry run, for orientation only. One core of a 2.3 GHz Xeon:

| Invoices | 360 searches, Python 3.13.18 | Slowest single search | The old enumerator on the same 360 ledgers |
| --- | --- | --- | --- |
| 8 | 0.05 s | under 1 ms | 0.63 s |
| 16 | 0.36 s | 5 ms | 266 s |
| 32 | 28.8 s | 0.40 s | not run |
| 64 | 48.2 s | 0.41 s | not run |

At 16 invoices the solver is several hundred times faster than the enumerator on these ledgers. Above 16 the enumerator cannot be run at all.

## 9. Edge cases and error handling

| Case | Required behaviour |
| --- | --- |
| `--timings` with the default sizes | Takes about five minutes, almost all of it the enumerator at 16 invoices. `--sizes 32,64` skips that part. |
| `--sizes 65` or `--sizes 7` | `ValueError` from `build_report`. Not caught. |
| A checkout with CRLF line endings | `--check` and the hash test normalize CRLF to LF before comparing |
| The two documents after a later change to a limit of `search` | `--check` exits 1. That is the purpose. The task that changes the limit regenerates the table with `--write --force` and reports the difference. |

Not covered by the experiment, on purpose: credits, several customers, and ledgers with no allocation. Each would add a dimension to a table that already has 72 rows. The credit and multi-customer behaviour of the solver is tested in RP-502 and RP-506.
