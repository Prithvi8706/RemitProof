## 1. Objective and rationale

Add 19 tests that state six invariants as properties of whole decisions and check them on generated cases and on the 80 legacy payments:

| Invariant | Property |
| --- | --- |
| INV-01 | Amounts are whole cents everywhere, sums are exact, and no float appears in a result |
| INV-03 | Free text in a proposal never changes a result |
| INV-07 | Whatever is proposed, at most one allocation can be decided for a fixed input |
| INV-10 | Without a usable proposal nothing is resolved |
| INV-15 | Adding inert records never changes a result |
| INV-16 | Reordering the input records never changes a result |

Until now INV-03, INV-15 and INV-16 were "not verified", and INV-15 had no exact meaning. This task fixes the input model for INV-15 and INV-16 (section 6.1 and 6.2). After it, the two invariants mean exactly what those sections say and nothing wider.

No application code changes. If a property fails, the application has a defect or the invariant is wrong. Either way the implementer stops and reports (section 16). The implementer never edits application code and never weakens a property to make it pass.

One thing differs from every earlier contract, and it is deliberate. Hypothesis in derandomized mode takes its examples from the source text of the test function. Two correct implementations of this contract therefore run different examples. So this contract pins no count that depends on generated examples. Where it gives such a number, it says "dry run" and gives a threshold that holds with a wide margin.

## 6. Input and output contracts

### 6.1 The input model of INV-16 (record order)

A reordering of a dataset is a dataset with the same records in which each of the five lists (payments, invoices, customers, credits, emails) is permuted independently. `shuffled(dataset)` draws five `st.permutations`, in that order of lists.

INV-16 then says: for every payment, `run` gives an equal result on the dataset and on every reordering of it.

Outside the model, on purpose: the order of IDs inside a proposal, and the order of sentences inside an email. Reordering sentences can change what an email means.

### 6.2 The input model of INV-15 (inert records)

Records added to a dataset are inert for a payment P when all five rules hold:

| # | Record | Rule | Free |
| --- | --- | --- | --- |
| 1 | Customer | A new customer ID. A legal name that shares no word with P's payer name (words compared after `casefold()`, split on whitespace). No known payers. | |
| 2 | Invoice | Belongs to an added customer. Its currency differs from P's currency. | Amount (it may equal P's amount), dates, status |
| 3 | Credit | Belongs to an added customer and is linked to an added invoice. | Amount, currency (it may equal P's), status |
| 4 | Email | A new email ID. Its customer is an added customer. Its sender domain is used by no existing email. Subject and body contain neither P's bank reference nor the ID of any existing record. | It may state P's amount and currency, carry P's date, and contain instruction sentences about added records |
| 5 | Payment | A new payment ID and a bank reference no existing payment has. | It may copy P's date, amount, currency and payer name |

INV-15 then says: `run` for P gives an equal result before and after the records are added.

The model is narrow on purpose. One step outside it, a result does change, and correctly so: an invoice of an unrelated customer in P's currency with exactly P's amount makes that customer a candidate. Test 13 pins that boundary, so that nobody reads INV-15 as "unrelated customers never matter".

### 6.3 `run`, `allocation`, `without_proposal`, `with_free_text`, `Scripted`

`Scripted.investigate(bundle)` returns `self.proposals[bundle.payment.payment_id]`, or raises `InvestigatorError("no proposal")` when the payment has no entry.

`run(dataset, payment_id, proposal)` calls `process_payment(payment_id, dataset, Scripted(...))` with `{payment_id: proposal}`, or with `{}` when the proposal is `None`. It returns `model_dump(mode="json")` of the result with `["decision"]["latency_ms"]` deleted. Every comparison of results in this task is a comparison of these dicts.

`allocation(result)` is `(decision["customer_id"], frozenset(decision["invoice_ids"]), frozenset(decision["credit_ids"]))`.

`without_proposal(result)` is the dict without its `proposal` key. The proposal is echoed into the result, so a test that edits the proposal's text compares everything else.

`with_free_text(data, proposal)` returns a copy of the proposal in which every semantic claim's `claim` is replaced by `data.draw(FREE_TEXT)` and `unresolved_questions` is `data.draw(st.lists(FREE_TEXT, max_size=3))`. Claims are drawn first, in order.

### 6.4 The legacy reference

Built once at import: `LEGACY_DATASET = load_dataset(REPO_ROOT / "data")`. `LEGACY_PROPOSALS` maps payment ID to the validated `InvestigationProposal` of every entry in `results/proposal_cache.json` (`entry["proposal"]` for each value of `["entries"]`). `LEGACY_RESULTS` maps every payment ID to `run(LEGACY_DATASET, payment_id, LEGACY_PROPOSALS.get(payment_id))`. Both files are read only.

## 8. Algorithm: the generators

Draws happen in the order written. "Draw" means `draw(...)` of the named Hypothesis strategy.

### 8.1 Helpers

`join_ids(["A"])` is `"A"`. `join_ids(["A", "B"])` is `"A and B"`. `join_ids(["A", "B", "C"])` is `"A, B and C"`.

`alternatives_of(dataset)` is `list(search(build_proof_set(dataset.payments[0], dataset)).alternatives)`.

`instruction_email(dataset, alternative, number)`: the body is `INSTRUCTION` with `ids=join_ids(sorted(alternative.invoice_ids))`. For each credit ID of the alternative in sorted order, append `CREDIT_INSTRUCTION` with that credit and the invoice it is linked to. The email has `email_id=f"EMAIL_{number}"`, `sender=SENDERS[alternative.customer_id]`, the alternative's customer, `date=EMAIL_DATE`, `subject="Remittance BNK-1"`.

### 8.2 `sentence_emails(dataset, number)`

1. Draw the customer from `["CUS_1", "CUS_1", "CUS_2"]`.
2. `own_invoices`: that customer's invoice IDs, sorted. `own_credits`: that customer's `(credit_id, invoice_id)` pairs, sorted.
3. Draw a count from 1 to 2. That many times:
   - draw a kind from `["invoice", "invoice", "invoice", "credit", "plain"]`;
   - kind `invoice` and `own_invoices` not empty: draw a unique list of 1 to 3 of them, then draw one of `INVOICE_SENTENCES`, and format it with `ids=join_ids(sorted(list))`;
   - kind `credit` and `own_credits` not empty: draw one pair, then draw one of `CREDIT_SENTENCES`, and format it;
   - otherwise the sentence is `PLAIN_SENTENCE`.
4. The email: `email_id=f"EMAIL_{number}"`, `sender=SENDERS[customer]`, that customer, `date=EMAIL_DATE`, `subject="Remittance BNK-1"`, body the sentences joined with one space.

### 8.3 `emails_for(dataset, mode=None)`

1. `alternatives = alternatives_of(dataset)`, before any draw.
2. If `mode` is `None`, draw it from `EMAIL_MODES`.
3. `none`: return `[]`.
4. `instruction`, and there are alternatives: draw an index into them. Start with `instruction_email(dataset, chosen, 1)`. Draw a boolean. If true, append a draw of `sentence_emails(dataset, 2)`. Return.
5. `instruction_per_customer`: for `CUS_1` and then `CUS_2`: if that customer has alternatives, draw an index into them and append `instruction_email(dataset, chosen, len(emails) + 1)`. Return, possibly empty.
6. Otherwise (`sentences`, or `instruction` with no alternative): draw a count from 1 to 2 and return `sentence_emails(dataset, number)` for `number` from 1 to the count.

### 8.4 `proposals_for(dataset)`

1. Draw the kind from `PROPOSAL_KINDS`. `unavailable`: return `None`.
2. `proof_set = build_proof_set(dataset.payments[0], dataset)` and `alternatives = search(proof_set).alternatives`.
3. `authorizable`: with `found = authorizable_allocations(proof_set.proof_bundle, alternatives)`, return `found[0][1]` if `found` is not empty, else `InvestigationProposal(payment_id="PAY_1")`.
4. `canonical`, and there are alternatives: draw an index and return `canonical_proposal(proof_set.proof_bundle, chosen)`.
5. Otherwise (`arbitrary`, or `canonical` with no alternative): draw the customer from `["CUS_1", "CUS_2"]`. The pools are all invoice IDs of the dataset, sorted; all credit IDs, sorted; and for evidence the sorted list of the customer ID, every email ID and every credit ID. Return a proposal for `PAY_1` with that customer, a drawn unique list of at most 3 invoice IDs (empty without a draw if the pool is empty), a drawn unique list of at most 2 credit IDs (same rule) and a drawn unique list of at most 4 evidence IDs.

### 8.5 `cases()`

1. Draw the shape from `CASE_SHAPES`.
2. Shape `any`: draw `ledgers()`. Otherwise draw `ledgers().filter(...)` keeping ledgers for which `alternatives_of` is not empty.
3. Shape `conflict`: append to the invoices an invoice `INV_2X` of `CUS_2` with the payment's amount, currency `USD`, issue date 2026-06-16, due date 2026-07-16 and description `Services`, and set `shared = True`. Otherwise draw `shared` as a boolean.
4. If `shared`: the second customer of the ledger gets `known_payers=["Acme Trading Ltd"]` (a copy, through `model_copy`).
5. Build the dataset without emails. Draw `emails_for(that dataset, mode)`, where `mode` is `"instruction_per_customer"` for shape `conflict` and `None` otherwise.
6. Build the dataset with those emails. Draw `proposals_for(dataset)`. Return `Case(dataset, proposal)`.

Why these choices. Shape `conflict` gives two customers who can each explain the payment and who each sent an instruction, which is the situation of finding F4. Instruction emails built from a real alternative make `resolved` reachable. Sentence emails make contradictions and unread instructions reachable. The `arbitrary` proposal names records the search never offered.

### 8.6 `inert_additions(dataset, payment_id)`

With `payment = dataset.payments_by_id[payment_id]`. Draw a number of customers from 1 to 3. For `number` from 1 to that count:

1. Customer `CUS_Z{number}` with `legal_name=INERT_NAMES[number - 1]`.
2. Draw an invoice count from 0 to 3. Invoice `index` (from 0): `INV_Z{number}{index}`, that customer, an amount drawn from `[payment.amount, Decimal("100.00"), Decimal("12345.67")]`, currency `INERT_CURRENCY`, an issue date drawn from `[date(2026, 6, 16), date(2026, 9, 1)]`, due date 2026-07-16, description `Services`, a status drawn from `["open", "paid", "closed"]`.
3. If the customer has invoices, draw a credit count from 0 to 2. Without invoices the count is 0 and nothing is drawn. Credit `index`: `CR_Z{number}{index}`, that customer, linked to an invoice drawn from the customer's own, an amount drawn from `[Decimal("50.00"), payment.amount]`, a currency drawn from `[INERT_CURRENCY, payment.currency]`, reason `Rebate`, a status drawn from `["valid", "invalid", "consumed"]`.
4. Draw an email count from 0 to 2. Email `index`: draw a sentence from `INERT_SENTENCES`. If it contains `{credit}` and the customer has no credit, use `INERT_SENTENCES[0]`. Then, if it contains `{invoice}` and the customer has no invoice, use `INERT_SENTENCES[3]`. The email: `EMAIL_Z{number}{index}`, `sender=f"ap@inert{number}.example"`, that customer, a date drawn from `[payment.date, date(2026, 1, 5)]`, `subject="Monthly statement"`, and the sentence formatted with the customer's first invoice ID, first credit ID, `payment.currency` and `format(payment.amount, "f")`.
5. Draw a boolean. If true, add a payment `PAY_Z{number}` with the date, amount and currency of `payment`, a payer name drawn from `[payment.payer_name, INERT_NAMES[number - 1]]` and `bank_reference=f"BNK-Z{number}"`.

Return a dataset in which each list is the original list followed by the additions.

Every drawn record satisfies section 6.2. The generator is one way to draw from the model. It is not the model.

## 9. Edge cases and error handling

| Case | Required behaviour |
| --- | --- |
| A ledger with no invoice or no alternative | Handled by the fall-through branches of 8.3 and 8.4. No draw is made from an empty pool. |
| `canonical` or `authorizable` proposal on a ledger with no alternative | The `arbitrary` branch, or the empty proposal |
| A generated case whose decision is `human_review` | Tests 10 and 11 pass it without a check on the allocation. That is why test 2 measures how often each decision occurs. |
| Hypothesis reports a health check | The three checks in `QUIET` are suppressed. Any other health check is a failure and is reported. |
| A second run | Gives the same examples and the same result. `derandomize=True`. |

Not covered: more than two real customers, emails in other languages or formats (RP-604), ledgers above the prompt cap of other kinds than `ledgers()` draws, and any property of the benchmark code.
