## 1. Objective and rationale

A comparison system: a language model alone, given every record of the case, allowed to answer "abstain". Its answer is taken as is. Nothing checks it.

Why it exists: the published comparison forced the model to answer every case, so it could only look bad. A fair model-only system must be able to say "a person should look at this". This baseline is that system.

What this task does not do. The first scope note also put two more things here: fixing the example identifiers in `backend/app/prompts/investigator.txt`, and bumping the freeze generation. That prompt is a frozen input and part of the identity of the 30 stored proposals. Changing it needs a live model to regenerate them, and it was not dry-run. It is now its own task, RP-307, with no contract yet. This task changes no frozen file.

## 3. Current behaviour and references

The product's investigator talks to an Ollama server with `urllib.request` and sends a JSON schema as `format` (`backend/app/services/ai_investigator.py:106-135`). Its prompt contains a worked JSON example with identifiers such as `INV_EXAMPLE_A` (`backend/app/prompts/investigator.txt:33-47`), and six stored proposals repeat those placeholders (`AUDIT_VALIDATION.md`, C4). This baseline's prompt therefore contains no example object and no identifier at all.

`INPUT_FIELDS` in `backend/remitbench/labelling.py` (RP-208) names the six record fields of a case.

## 6. Input and output contracts

### 6.1 Prompt file

`backend/remitbench/prompts/abstaining_baseline.txt`: 1,481 bytes, SHA-256 `794f62a662fa4bac2370f9fc72315241f56d80ea55b08c40102e8274f2644c7f`, LF line endings, one final newline. Exactly this text:

```
You are an accounts-receivable clerk. You are given one incoming payment, the open ledger around it, and any messages about it, as JSON.

Decide what to do with the payment.

Answer "allocate" only if a careful clerk holding exactly these records would post the payment without asking anyone. Then name the customer, the invoices it pays, and any credit notes used.

Answer "abstain" in every other case. Abstaining is a normal and correct answer. It means a person should look at this payment.

Rules:
1. Exact amounts only. The chosen invoices minus the chosen credit notes must equal the payment amount exactly. There are no part payments, no payments on account and no rounding.
2. One customer per allocation.
3. No default habits. If two different sets of invoices fit and nothing from the customer says which, abstain.
4. An invoice can be paid only if it is open, not already allocated, in the payment's currency, and issued on or before the payment date.
5. A credit note can be used only if it is valid, not already used, and belongs to one of the chosen invoices.
6. Use only identifiers that appear in the records you were given, copied exactly.

Return one JSON object with these fields and nothing else:
- decision: "allocate" or "abstain"
- customer_id: the customer identifier, or null when you abstain
- invoice_ids: a list of invoice identifiers, empty when you abstain
- credit_ids: a list of credit note identifiers, possibly empty
- reason: one short sentence
```

Its rules 1 to 5 are the rules of the authoring guide (RP-203), so the model is told the same world the labels were written in.

### 6.2 `AbstainingAnswer`

One `@model_validator(mode="after")`: if `decision == "allocate"` and (`customer_id is None` or `invoice_ids` is empty), raise `ValueError("an allocate answer needs customer_id and at least one invoice")`.

### 6.3 `http_transport(url, payload, timeout_seconds)`

Builds `request.Request(url, data=json.dumps(payload).encode("utf-8"), headers={"Content-Type": "application/json"}, method="POST")`, opens it with `request.urlopen(call, timeout=timeout_seconds)`, and returns `json.loads(response.read().decode("utf-8"))`. It catches nothing.

### 6.4 `AbstainingModel`

`__init__` stores `host.rstrip("/")`, `model`, `model_digest`, `timeout_seconds`, `transport`, and reads the prompt file once into `self.system_prompt` (UTF-8).

`provenance()` returns a dictionary with these keys in this order:

| Key | Value |
| --- | --- |
| `baseline_version` | `BASELINE_VERSION` |
| `model` | The model name |
| `model_digest` | The digest, or `None` |
| `host_sha256` | Hex SHA-256 of the stored host string. The host itself is never returned: a URL can carry credentials. |
| `generation_options` | A copy of `GENERATION_OPTIONS` |
| `prompt_sha256` | Hex SHA-256 of `self.system_prompt` in UTF-8 |
| `answer_schema_sha256` | Hex SHA-256 of `json.dumps(AbstainingAnswer.model_json_schema(), sort_keys=True, separators=(",", ":"))` in UTF-8 |

`answer(case)`:

1. `data = case.model_dump(mode="json")`; `records = {name: data[name] for name in INPUT_FIELDS}`.
2. `payload`, keys in this order: `model`; `messages` = a system message with the prompt and a user message with `json.dumps(records, separators=(",", ":"), ensure_ascii=False)`; `stream` = `False`; `format` = `AbstainingAnswer.model_json_schema()`; `options` = a copy of `GENERATION_OPTIONS`.
3. Inside one `try`: `result = self.transport(f"{self.host}/api/chat", payload, self.timeout_seconds)`, then return `AbstainingAnswer.model_validate(json.loads(result["message"]["content"]))`.
4. `except (OSError, KeyError, TypeError, ValueError, ValidationError) as error: raise ModelError(type(error).__name__) from None`.

One request per case. No retry. The `ModelError` message is the exception class name only: an error text could quote the request.

The request carries the six record fields and nothing else of the case: no label, no author, no seed ID, no variant.

### 6.5 `llm_abstain(model)`

Returns a function of a case: on `ModelError` return `review(case, "model_unavailable")`; if the answer's decision is `abstain` return `review(case, "model_abstained")`; otherwise `allocate(case, answer.customer_id, answer.invoice_ids, answer.credit_ids)`.

The answer is not checked against the ledger. An identifier that does not exist is passed through and scored as a wrong allocation.
