## 1. Objective and rationale

Add Hypothesis to the development dependencies so that RP-106 can add property tests.

Why this is its own task: CI installs from `backend/requirements-dev.lock` with hash checking, and that lock was compiled under Python 3.9. Adding a line to the `.in` file is not enough. The lock must be regenerated under Python 3.9, and the result must add packages without removing or changing any.

The version is pinned to `6.141.1`. It is the newest Hypothesis release that still supports Python 3.9 (resolved with `pip download hypothesis --python-version 3.9` during the dry run; the newest release overall at that time was 6.170.15 and does not support 3.9). Keeping Python 3.9 in CI is owner decision OD-1. If the owner drops 3.9, this pin can be raised in a later task.

This task adds no test. Runtime dependencies (`backend/requirements.in`, `backend/requirements.lock`) do not change.

## 3. Current behaviour and references

`backend/requirements-dev.in` has a two-line comment followed by `-r requirements.in` and `pytest==8.3.5`.

`backend/requirements-dev.lock` starts with a header that records how it was made:

```
# This file is autogenerated by pip-compile with Python 3.9
# by the following command:
#
#    python -m piptools compile --generate-hashes --strip-extras --output-file=backend/requirements-dev.lock backend/requirements-dev.in
```

The lock contains a `colorama==0.4.6` block. `colorama` is a Windows-only dependency of `click` and `pytest`, which shows the lock was compiled on Windows. Compiling on Linux or macOS drops that block. A lock without it fails to install with `--require-hashes` on Windows. Section 9 says what to do.

CI (`.github/workflows/ci.yml`) installs the lock under Python 3.9 and 3.13, runs `python -m pip check`, then the suite.

Hypothesis creates a `.hypothesis/` directory in the working directory when tests run, even with its example database disabled. It must be ignored by git.

## 7. Implementation steps

Run every command from the repository root.

1. Append the line to `backend/requirements-dev.in`.
2. Compile under Python 3.9 with the header command pinned. On Linux or macOS:

```
CUSTOM_COMPILE_COMMAND="python -m piptools compile --generate-hashes --strip-extras --output-file=backend/requirements-dev.lock backend/requirements-dev.in" python3.9 -m piptools compile --generate-hashes --strip-extras --output-file=backend/requirements-dev.lock backend/requirements-dev.in
```

On Windows PowerShell:

```
$env:CUSTOM_COMPILE_COMMAND = "python -m piptools compile --generate-hashes --strip-extras --output-file=backend/requirements-dev.lock backend/requirements-dev.in"
py -3.9 -m piptools compile --generate-hashes --strip-extras --output-file=backend/requirements-dev.lock backend/requirements-dev.in
```

Do not pass `--upgrade`. Without it, pip-tools keeps every existing pin.

3. Inspect `git diff backend/requirements-dev.lock` against section 6. Apply section 9 if needed.
4. Append the line to `.gitignore`.
5. Run the commands in section 13.

## 9. Edge cases and error handling

| Case | Required behaviour |
| --- | --- |
| The diff removes the `colorama==0.4.6` block (you compiled on Linux or macOS) | Restore that block exactly as it is in `git show HEAD:backend/requirements-dev.lock`: the name line, its two hash lines and its three comment lines, at the same position (directly before the `exceptiongroup` block). After restoring, the diff must have no deleted line. This happened in the dry run. |
| The diff changes the version or a hash of any existing package | Stop. Do not commit the lock. Report the package names. |
| The diff removes any block other than `colorama` | Stop. Report. |
| The header lines differ from the committed header | `CUSTOM_COMPILE_COMMAND` was not set. Restore the file with `git checkout backend/requirements-dev.lock` and repeat step 2. |
| `pip check` reports a conflict | Stop. Report the full output. |
