## 1. Objective and rationale

Close finding F5. Today the rules-only matcher can apply a payment to invoices that a fully read remittance instruction from the same customer does not name. Example: payment 10000.00, open invoices `INV_A` 6000.00 and `INV_C` 10000.00, and the customer writes "Apply BNK-1 only to INV_A." The result is `matched_normally` on `INV_C`.

The proof engine already knows that this is a contradiction. It holds it against every proposal (`backend/app/services/proof_engine.py:392` to `:398`). The matcher never asks.

The rule after this task: **a rules-only match is made only if the proof of the matched allocation shows no contradiction.** The proof is the one the proof engine computes for the canonical proposal of that allocation (RP-110). If it shows a contradiction, the match is refused, the matcher's result becomes "unresolved", and the payment continues exactly as an unmatched payment does today: to the investigator, and through the gate.

This serves INV-08 (a contradiction with a relevant instruction blocks) on the path where it did not hold, and it brings the two automatic paths under one definition of contradiction.

A wider rule was tried in the dry run and rejected: "a match must be the one authorizable allocation" (the predicate of RP-110). It refuses a plain payer-name match whenever any unrelated customer has an open invoice of the same amount, because the sufficiency gate counts that invoice as a second explanation. That would send many ordinary payments to review on a large ledger. The control test of RP-601 (test 13) caught it. The narrow rule changes that test not at all.

## 6. Input and output contracts

### 6.1 `match_contradictions`

Find the first alternative for which all three hold: its `customer_id` equals `baseline.customer_id`; the set of its `invoice_ids` equals the set of `baseline.matched_invoices`; the set of its `credit_ids` equals the set of `baseline.matched_credits`.

- Found: return `list(verify_candidate(bundle, canonical_proposal(bundle, alternative)).contradictions)`.
- Not found: return `["matched allocation is not among the alternatives"]`.

The second case cannot happen through the pipeline, because the matcher chooses its match from the alternatives it is given. It is defined so that the function fails closed if that ever stops being true.

### 6.2 The pipeline

Directly after the statement `baseline = baseline_match(...)` (`pipeline.py:139` in the dry-run tree) and before the `if baseline.status == "matched":` that follows it, insert one statement:

If `baseline.status == "matched"` and `match_contradictions(proof_bundle, baseline, outcome.alternatives)` is not empty, replace `baseline` by `BaselineResult(payment_id=payment.payment_id, status="unresolved", reason="conflicting_remittance_evidence", candidate_count=baseline.candidate_count)`.

Nothing after that point changes. A refused match falls through the existing `if baseline.status == "matched":` and continues as an unmatched payment.

## 9. Edge cases and error handling

| Case | Required behaviour |
| --- | --- |
| The matched customer sent an instruction that names exactly the matched invoices | No contradiction. The match stands. |
| The matched customer sent an email with no identifier and no instruction | No contradiction. The match stands. This is finding F7 when the email is a hold, and this task does not change it. |
| Two emails of the matched customer, one naming the matched invoices and one naming others | Contradiction from the second. The match is refused. |
| A candidate email filed under another customer names other invoices | Not counted. The proof engine looks only at the emails of the proposed customer, and the matcher at the emails of customers it recognises as the payer. The match stands. Stated limit, pinned by test 7. |
| An older instruction superseded by a trusted, dated correction | Not counted, by the proof engine's own rule. Not tested here: the existing tests of the proof engine cover superseding. |
| A refused match, then a proposal that names the same allocation | `human_review` with reason `contradictory_evidence`, from the existing gate |
| A refused match, and the investigator is unavailable | `human_review` with the existing unavailable reason |
