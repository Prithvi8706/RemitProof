## 1. Objective and rationale

Today the reason on a `human_review` decision describes the proposal that was judged, not the payment. If the model proposes the wrong invoice, the reviewer reads why that wrong proposal failed. If no model is present, the reviewer reads a sentence about the missing investigator.

This task adds one function, `assess_case`, that answers from the case alone, without any proposal:

1. Can this payment be decided automatically at all?
2. If yes, which allocation is the only one that can be decided?
3. If no, what is the first thing that stops it?

It is a new module that nothing on the decision path calls. `process_payment` is not changed and no `Decision` changes. RP-803 is the task that may publish the assessment, because it is the only task allowed to change the result shape.

What the dry run measured on the 80 legacy payments, with the cached proposals. This is the reason the task exists:

| Published decision | Assessment of the case | Payments |
| --- | --- | --- |
| `matched_normally` | automatic, `rules_only_match`, same allocation | 50 |
| `resolved` | automatic, `single_authorizable_allocation`, same allocation | 12 |
| `human_review` | automatic, `single_authorizable_allocation` | 6 |
| `human_review` | needs review, `no_authorizable_allocation` | 6 |
| `human_review` | needs review, `no_financially_valid_allocation` | 6 |

Read the third row plainly. Six payments are in review although exactly one allocation is authorizable: `PAY_053`, `PAY_064`, `PAY_066`, `PAY_072`, `PAY_078`, `PAY_080`. The cached proposal for each named something else, and the published reason describes that wrong proposal. The legacy truth labels say all six should have been resolved. So the assessment agrees with the truth label `should_resolve` on all 80 payments, and it never reads that label.

Of the 12 payments that do need review, the published reason equals the reason the case gives for 5 (`PAY_058`, `PAY_060`, `PAY_062`, `PAY_073`, `PAY_075`) and differs for 7. In total the published review reason is not the case's reason for 13 of 18 legacy review decisions.

One statement of limits, so that the table is not over-read: 80 payments written by the author of the system. It shows that the assessment is consistent with the existing labels. It is not evidence about real payments.

Change from the plan. The plan marked this task as changing authorization-critical code, with the reason written into `Decision.reason`. It is written as a read-only module for two reasons. `Decision.reason` is part of the published legacy snapshot, which is frozen until RP-803. And a module that cannot change a decision can be compared with the pipeline by a property test (test 9), which is stronger than trusting an edit inside the pipeline.

## 6. Input and output contracts

### 6.1 `assess_case`

Unknown payment: `KeyError(f"Unknown payment: {payment_id}")`, the message `process_payment` uses.

"Review with reason R" below means a `CaseAssessment` with `reason=R`, `automatic=None`, `allocation=None`, and the counts and `blocked_by` given in the row. Where a row gives none, the counts are 0 and `blocked_by` is `()`.

The checks, in this order. The first that applies decides.

| # | Condition | Result |
| --- | --- | --- |
| 1 | The payment ID is in `dataset.replayed_payment_ids` | Review, `duplicate_bank_transaction` |
| 2 | `search(build_proof_set(payment, dataset))` has status `unknown` | Review, `search_incomplete` |
| 3 | `find_unread_instructions(proof_bundle).blocks` | Review, `unread_instruction` |
| 4 | `baseline_match(proof_bundle, alternatives=alternatives)` is `matched` and `match_contradictions(proof_bundle, baseline, alternatives)` is empty | Automatic, `rules_only_match`. `allocation` is the match. `alternative_count` is the number of alternatives. `authorizable_count` is 0: it is not computed on this path. |
| 5 | `payment.status != "unmatched"` | Review, `payment_not_unmatched`, with `alternative_count` |
| 6 | There is no alternative | Review, `no_financially_valid_allocation`. `blocked_by` is `(named_allocation_reason(proof_bundle),)`, or `()` when that is `None`. |
| 7 | `authorizable_allocations(proof_bundle, alternatives)` has exactly one entry | Automatic, `single_authorizable_allocation`. `allocation` is that entry's alternative. `authorizable_count` is 1. |
| 8 | It has more than one entry | Review, `multiple_authorizable_allocations`, with both counts |
| 9 | It has none | Review, `no_authorizable_allocation`, with `alternative_count`. `blocked_by` is the sorted set of blocking reasons of all alternatives (below). |

`alternatives` is the list of the search outcome's alternatives. `proof_bundle` is `proof_set.proof_bundle`. The proof set is built before check 1, as `process_payment` does.

The blocking reason of one alternative: build `canonical_proposal(proof_bundle, alternative)`, verify it with `verify_candidate`, evaluate it with `evaluate_evidence_sufficiency(proof_bundle, proposal, proof, alternatives)`, and take `abstention_reason`. If that is `None`, take `"evidence_not_sufficient"`.

The `allocation` tuple is `(customer_id, tuple(sorted(invoice_ids)), tuple(sorted(credit_ids)))`.

### 6.2 `named_allocation_reason`

It answers: the documents name an allocation, no exact allocation exists, so why does the named one fail?

1. Collect texts. First the payment's `bank_reference` and `remittance_reference` joined by one space, read with `bare_references_are_affirmative=True`. Then, for each candidate email, `f"{email.subject} {email.body}"` read with `bare_references_are_affirmative=False`.
2. From `classify_document_semantics` of each text take `affirmative_invoice_ids` and `affirmative_credit_ids`, and unite them over all texts.
3. If no invoice ID was found, return `None`.
4. `owners` is the sorted set of `customer_id` of the candidate invoices whose ID is among the named invoice IDs.
5. Build an `InvestigationProposal` for the payment: `proposed_customer` is the one owner, or `None` when there is not exactly one; `invoice_ids` and `credit_ids` are the named IDs, sorted; `evidence_ids` is the sorted list of that one owner (if there is one) and the IDs of all candidate emails.
6. Verify it and evaluate it with `evaluate_evidence_sufficiency(bundle, proposal, proof, [])`. Return its `abstention_reason`, or `"evidence_not_sufficient"` when that is `None`.

The email flag in step 1 matters. An ID that stands alone in an email is not an instruction. It is an unread instruction (check 3), and it must not be treated as naming an allocation. Test 7 pins this.

## 9. Edge cases and error handling

| Case | Required behaviour |
| --- | --- |
| A match that RP-606 refuses | Check 4 does not apply. The case continues to checks 5 to 9, as the pipeline continues to the investigator. Test 4. |
| A matched payment whose status is not `unmatched` | Cannot occur: the matcher returns `payment_not_unmatched` for such a payment and never matches it (`backend/app/services/baseline_matcher.py:55`). Check 5 therefore reports it. |
| No alternative and the documents name nothing | `no_financially_valid_allocation` with `blocked_by == ()` |
| No alternative and the named invoice is unknown to the ledger | `blocked_by == ("unsupported_entity_relationship",)` |
| An automatic case and a model that proposes something else | The assessment still says automatic. The pipeline sends the payment to review. That difference is the point of the task, and test 9 allows it: an automatic case must be decided for at least one proposal, not for every proposal. |
| The assessment and the pipeline disagree in the other direction: the case "needs review" but some proposal is decided | Must never happen. Test 9 fails. |
