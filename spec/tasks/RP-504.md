## 1. Objective and rationale

Give `solve` an optional `node_budget`. With a budget of `b` the search visits at most `b` nodes. If it would need one more, it stops and returns the third status, `node_budget`.

Why: the search is exponential in the worst case (RP-502 section 8.7). A ledger of 40 equal invoices with a payment that fits no combination has more than a hundred billion subsets to rule out, and the two bounds cut none of them early. Without a budget the pipeline would not return. INV-12 says what must happen: a budget maps to `unknown`, and `unknown` maps to human review. This task provides the solver's half: an honest status. RP-507 maps it to `unknown`.

The budget counts nodes, not time. A node count is the same on every machine and every run, so the outcome for a given ledger never depends on how busy the machine is (R-09). The price is that the time a budget stands for differs between machines. RP-508 measures it.

This task changes one function. Nothing consumes the solver yet. No decision changes.

## 5. Interfaces

```
STATUS_COMPLETE = "complete"                  # unchanged
STATUS_SOLUTION_LIMIT = "solution_limit"      # unchanged
STATUS_NODE_BUDGET = "node_budget"            # new

class _Stop(Exception):                       # now built with the status that caused it
    def __init__(self, status: str) -> None

def solve(
    problem: Problem,
    solution_limit: Optional[int] = None,
    node_budget: Optional[int] = None,
) -> SolveResult
```

`_Stop.__init__` stores its argument as `self.status`.

## 6. Input and output contracts

### 6.1 `solve(problem, solution_limit, node_budget)`

Argument checks, in this order:

1. `solution_limit` below 1: `ValueError("solution_limit must be at least 1")` (RP-503).
2. `node_budget` is not `None` and is below 1: `ValueError("node_budget must be at least 1")`.
3. Groups present and `target < 1`: `ValueError("target must be at least 1")` (RP-502).

Result:

| Situation | `status` | `solutions` | `nodes` |
| --- | --- | --- | --- |
| `node_budget` is `None` | As in RP-503 | As in RP-503 | As in RP-503 |
| The whole search needs at most `node_budget` nodes | As without a budget | As without a budget | As without a budget |
| The solution limit is reached at or before node number `node_budget` | `solution_limit` | As in RP-503 | As in RP-503 |
| Otherwise | `node_budget` | The allocations found in the first `node_budget` nodes, sorted ascending | Exactly `node_budget` |

What `node_budget` means, and nothing more: the search was cut off. The returned allocations exist. How many more exist is not known, and "none found" does not mean "none exists". No caller may read `none` or `unique` from this status.

The budget is one counter for the whole call, across groups.

## 7. Implementation steps

1. Add the constant. Give `_Stop` the `status` argument. Change the solution-limit stop to `raise _Stop(STATUS_SOLUTION_LIMIT)`.
2. Add the parameter and the argument check.
3. At the top of `visit`, before the node is counted: if `node_budget` is not `None` and `nodes >= node_budget`, raise `_Stop(STATUS_NODE_BUDGET)`.
4. Change the handler to `except _Stop as stop:` and set the status to `stop.status`.
5. Create the tests in section 12.
6. Run section 13.

## 8. Algorithm

```
visit(i, net):
    if node_budget is not None and nodes >= node_budget:
        raise _Stop("node_budget")
    nodes += 1
    ... bounds, end of list (with the solution-limit stop), options, skip: unchanged ...
```

The check comes before the count. So a search that needs exactly `node_budget` nodes finishes and is `complete`, and a search that is cut off reports exactly `node_budget` nodes.

Why the budget cannot produce a wrong answer. It adds no allocation and removes none from the list: recording is unchanged. It can only end the search. Every path out of the search that is not the natural end goes through `_Stop`, and the status after a `_Stop` is never `complete`.

Worked example, continued from RP-502 section 8.6 (15 nodes, allocations found at nodes 7 and 12):

| `node_budget` | Status | Allocations returned | `nodes` |
| --- | --- | --- | --- |
| 16 | `complete` | Both | 15 |
| 15 | `complete` | Both | 15 |
| 14 | `node_budget` | Both | 14 |
| 12 | `node_budget` | Both | 12 |
| 11 | `node_budget` | The first | 11 |
| 7 | `node_budget` | The first | 7 |
| 6 | `node_budget` | None | 6 |
| 1 | `node_budget` | None | 1 |

Read the row for 14. Both allocations are in hand and the status is still `node_budget`: one node was left unvisited, so the list is not proven complete. Read the row for 6. No allocation was found, and one exists.

With both arguments on the same example:

| `solution_limit` | `node_budget` | Status | Allocations | `nodes` |
| --- | --- | --- | --- | --- |
| 2 | 12 | `solution_limit` | 2 | 12 |
| 2 | 11 | `node_budget` | 1 | 11 |
| 1 | 7 | `solution_limit` | 1 | 7 |
| 1 | 6 | `node_budget` | 0 | 6 |
| 3 | 15 | `complete` | 2 | 15 |
| 3 | 14 | `node_budget` | 2 | 14 |

## 9. Edge cases and error handling

| Case | Required behaviour |
| --- | --- |
| The budget runs out in the first group | Later groups are not searched |
| The budget runs out in a later group | Allocations of earlier groups are in the returned list |
| The same call repeated | The same result. `solve` keeps no state between calls. |
| `node_budget=0` or negative | `ValueError`, before anything is searched |
| An exception other than `_Stop` inside the search | Not caught |
