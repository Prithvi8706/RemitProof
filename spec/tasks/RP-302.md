## 1. Objective and rationale

Three pieces in `backend/remitbench/`.

1. `systems.py`: a system is a function from a case to a decision. Two systems need no model: `rules_only` and `verifier_only`. A third, `proposal_pipeline`, wraps any investigator. A run of a system is written to a decisions file.
2. `scoring.py`: one decision against one gold label gives one of four outcomes. A set of outcomes gives the metrics, with intervals from RP-301.
3. `backend/scripts/remitbench_eval.py run`: runs a model-free system over a directory of cases.

Why decisions files: scoring is separated from running. A system that needs a model, an old commit or another machine only has to produce the same small file. The file holds identifiers and reason codes, no gold label and no message text, so it can be kept and compared freely.

Why the legacy evaluator is not touched (DD-21): `backend/app/services/evaluator.py` produces the published snapshot. This harness is new code beside it.

Definitions fixed by this task:

| Term | Definition |
| --- | --- |
| Wrong allocation (false authorization) | The system allocated, and the label is `review` or names a different customer, invoice set or credit set |
| False authorization rate | Wrong allocations divided by all cases in scope. Exact interval and one-sided upper bound. |
| Automation error | Wrong allocations divided by automatic decisions in scope |
| Coverage | Correct allocations divided by cases whose label is `allocate` |
| Easy case | A case the rules-only system allocates correctly. Every other case is an exception. |

An easy case is defined by a correct rules-only allocation, not by any rules-only allocation. A case the rules-only system allocates wrongly stays in the exception set, where it is counted.

## 3. Current behaviour and references

`run_case(case, investigator)` returns a `ProcessingResult` (`backend/remitbench/adapter.py`, RP-204). Its `decision.decision` is `matched_normally`, `resolved` or `human_review`. `decision.reason` and `baseline.reason` are strings. `VerifierOnlyInvestigator` is in `backend/app/services/verifier_only.py` (RP-003, changed by RP-110). `InvestigatorError` is at `backend/app/services/ai_investigator.py:24`.

When the investigator raises `InvestigatorError`, the pipeline returns human review with the reason `Investigator unavailable; no autonomous action is allowed.` That sentence describes the missing model, not the case. The rules-only system therefore reports `baseline.reason` for a review.

```python
@dataclass(frozen=True)
class SystemDecision:
    case_id: str
    action: str
    customer_id: Optional[str]
    invoice_ids: Tuple[str, ...]
    credit_ids: Tuple[str, ...]

def review(case: BenchCase, reason: str) -> SystemDecision

def verifier_only(case: BenchCase) -> SystemDecision
def proposal_pipeline(investigator: Investigator) -> System
MODEL_FREE_SYSTEMS: Dict[str, System] = {"rules_only": rules_only, "verifier_only": verifier_only}
def run_system(system: System, cases: Sequence[BenchCase]) -> List[SystemDecision]
def dump_decisions(decisions: Sequence[SystemDecision]) -> str

```

`backend/remitbench/scoring.py`:

```python
OUTCOMES = ("correct_allocation", "wrong_allocation", "correct_review", "false_escalation")
```

## 6. Input and output contracts

### 6.1 Decisions

`allocate(case, customer_id, invoice_ids, credit_ids)`: `SystemDecision(case.case_id, "allocate", customer_id, tuple(sorted(invoice_ids)), tuple(sorted(credit_ids)), None)`.

`review(case, reason)`: `SystemDecision(case.case_id, "review", None, (), (), reason)`.

`decision_from_result(case, result)`: if `result.decision.decision` is `matched_normally` or `resolved`, `allocate(case, decision.customer_id, decision.invoice_ids, decision.credit_ids)`; otherwise `review(case, decision.reason)`.

### 6.2 Systems

`rules_only(case)`: `result = run_case(case, NoModel())`. If `result.decision.decision == "matched_normally"` return `decision_from_result(case, result)`. Otherwise `review(case, result.baseline.reason)`.

`verifier_only(case)`: `decision_from_result(case, run_case(case, VerifierOnlyInvestigator()))`.

`proposal_pipeline(investigator)`: returns a function that maps a case to `decision_from_result(case, run_case(case, investigator))`.

`run_system(system, cases)`: for each case in ascending case ID, call the system. If the returned `case_id` differs from the case's, or `action` is not in `ACTIONS`, raise `ValueError(f"{case.case_id}: the system returned a malformed decision")`. Return the list.

### 6.3 Decisions file

`dump_decisions(decisions)`: one line per decision, ascending case ID. Each line is `json.dumps(..., ensure_ascii=False)` of a dictionary with exactly these keys in this order: `case_id`, `action`, `customer_id`, `invoice_ids` (list), `credit_ids` (list), `reason`. Each line ends with `\n`. No indent, default separators.

`write_decisions(path, decisions)`: creates parent directories, writes the dump as UTF-8 bytes.

`read_decisions(path)`: for each line, numbered from 1, skipping lines that are blank after `strip()`:

| Condition | Raises `ValueError` with |
| --- | --- |
| The key set is not exactly the six keys | `line <n>: unexpected keys` |
| `action` is not in `ACTIONS` | `line <n>: unknown action` |
| The case ID was already read | `line <n>: second decision for <case_id>` |

Returns a dictionary from case ID to `SystemDecision`, with ID lists sorted into tuples.

### 6.4 `outcome(case, decision)`

| Decision | Label | Outcome |
| --- | --- | --- |
| `allocate` | `allocate`, and `customer_id` equal, and `decision.invoice_ids == tuple(sorted(gold.invoice_ids))`, and the same for credits | `correct_allocation` |
| `allocate` | Anything else | `wrong_allocation` |
| `review` | `review` | `correct_review` |
| `review` | `allocate` | `false_escalation` |

The system's review reason plays no part in the outcome. Whether the reason matches the label's family is a separate metric and is not part of this task.

### 6.5 `check_complete` and `easy_case_ids`

`check_complete(cases, decisions)`: if some case has no decision, raise `ValueError(f"{len(missing)} cases have no decision; first: {missing[0]}")` with `missing` sorted. Then, if a decision names no case, raise `ValueError(f"{len(extra)} decisions name unknown cases; first: {extra[0]}")`.

`easy_case_ids(cases, rules_only_decisions)`: the set of case IDs whose `outcome` under the given decisions is `correct_allocation`.

### 6.6 `metrics(cases, decisions)`

Returns a dictionary with these keys in this order:

| Key | Value |
| --- | --- |
| `cases` | Number of cases |
| `seeds` | Number of distinct seed IDs |
| `gold_allocate` | Cases labelled `allocate` |
| `gold_review` | Cases labelled `review` |
| `outcomes` | Count per outcome, keys in `OUTCOMES` order |
| `false_authorization` | Proportion: wrong allocations over all cases. Exact. |
| `automation_error` | Proportion: wrong allocations over correct plus wrong allocations. Exact. |
| `coverage` | Proportion: correct allocations over `gold_allocate`. Wilson. |
| `correct_review` | Proportion: correct reviews over `gold_review`. Wilson. |

A proportion with denominator 0 is `None`. Otherwise it is a dictionary with these keys in this order:

| Key | Value |
| --- | --- |
| `k`, `n` | Numerator and denominator |
| `rate` | `k / n` |
| `interval_95` | `[low, high]`: `clopper_pearson(k, n)` for an exact proportion, `wilson(k, n)` otherwise |
| `upper_95_one_sided` | `upper_bound(k, n)`. Present only for an exact proportion. |
| `seed_interval_95` | `[low, high]` from `cluster_bootstrap(groups)` with its default arguments, or `None` when it returns `None` |
| `seed_resamples_kept` | The third element of the bootstrap result, or 0 |

`groups` for the bootstrap: one `(numerator, denominator)` pair per seed, seeds in ascending ID, where numerator and denominator are the same two quantities as `k` and `n` counted inside that seed.

The result does not depend on the order of `cases`. `metrics` does not call `check_complete`: a missing decision raises `KeyError`.

### 6.7 Command `run`

| Situation | Printed | Return |
| --- | --- | --- |
| `--out` exists | `refusing to overwrite <resolved path>` | 2 |

## 8. Algorithm

`metrics`: one pass over the cases to count outcomes overall and per seed, then four calls that build the proportions. The bootstrap index rows are cached by RP-301, so four proportions over the same seeds cost one index computation.

## 9. Edge cases and error handling

| Case | Required behaviour |
| --- | --- |
| A system allocates on a case labelled `review` | `wrong_allocation`, whatever it allocated |
| A system allocates the right invoices and omits a labelled credit | `wrong_allocation` |
| IDs in another order | Equal. Both sides are sorted. |
| No automatic decision in scope | `automation_error` is `None` |
| No case in scope | `cases` is 0 and all four proportions are `None` |
| An investigator raises something other than `InvestigatorError` | Propagates out of `run_system`. A run that crashes writes no file. |
