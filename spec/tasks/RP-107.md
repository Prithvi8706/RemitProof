## 1. Objective and rationale

Add a field `unread_ids` to `DocumentSemantics`. It holds every invoice or credit ID that appears in a clause the reader could not classify as affirmative, negated or non-current.

Why: finding F2. In "This transfer settles INV_C in full. We will use a separate transfer for INV_A and INV_B next month." the reader does not know the verb "settles", so it records nothing about `INV_C`, and it reads the second sentence as the instruction. The reader's silence about `INV_C` is the signal. Today that signal is discarded. This task records it. RP-108 acts on it.

Nothing reads the new field in this task. No decision changes.

## 3. Current behaviour and references

`DocumentSemantics` (`backend/app/utils/remittance_semantics.py:226`) is a plain dataclass with seven set-valued fields, the last being `prohibited_credit_amounts` (`backend/app/utils/remittance_semantics.py:234`).

`classify_document_semantics` (`backend/app/utils/remittance_semantics.py:429`) splits the text into clauses and, per clause, computes three booleans: `is_negated`, `is_noncurrent`, `is_affirmative`. It then fills the result. The last block (`backend/app/utils/remittance_semantics.py:459` to `:463`) adds the clause's IDs to the affirmative sets when the clause is not negated, not non-current, and either affirmative or read in bare-reference mode. The function returns at `backend/app/utils/remittance_semantics.py:464`.

A clause that is none of the three, read without bare-reference mode, contributes its IDs to no field. That is the gap.

Callers that pass `bare_references_are_affirmative=True` read the payment's own reference fields. In that mode every non-negated, non-current clause is affirmative by definition, so no ID can be unread.

## 6. Input and output contracts

For each clause, with `invoice_ids`, `credit_ids`, `is_negated`, `is_noncurrent`, `is_affirmative` as the function already computes them:

- If all four of these are false: `is_negated`, `is_noncurrent`, `is_affirmative`, `bare_references_are_affirmative`, then add every ID in `invoice_ids` and `credit_ids` to `result.unread_ids`.
- Otherwise add nothing.

The rule is per clause. An ID that is affirmative in one clause and appears again in an unclassified clause is in both `affirmative_invoice_ids` and `unread_ids`.

The seven existing fields are computed exactly as before.

## 8. Algorithm

```
for clause in clauses(text):
    ... existing code, unchanged ...
    if not is_negated and not is_noncurrent and not is_affirmative \
            and not bare_references_are_affirmative:
        result.unread_ids.update(invoice_ids)
        result.unread_ids.update(credit_ids)
```

## 9. Edge cases and error handling

| Case | Required behaviour |
| --- | --- |
| Clause with no ID | Adds nothing |
| Bare-reference mode | `unread_ids` is always empty |
| Clause that is negated or non-current | Its IDs are not unread: the reader classified them |
| Empty or `None` text | Empty result |
| Credit amounts in an unclassified clause | Not recorded. Only IDs are recorded. |
