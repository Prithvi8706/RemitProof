## 1. Objective and rationale

Three things.

1. `backend/remitbench/oracle.py`: an exhaustive search for every allocation that explains a payment exactly. It is written from the definition and shares no code with the pipeline's enumerator.
2. `backend/remitbench/validate.py`: checks on one case, on one seed, and on a directory.
3. `backend/scripts/remitbench_validate.py`: a command that prints the issues and exits non-zero when there are any.

Why an own oracle: the benchmark judges the system. If the benchmark asked the system's enumerator whether a label is arithmetically possible, an enumerator defect would hide itself. The oracle is slow and simple on purpose.

Why messages carry identifiers only: the same validator runs on the sealed test split. A message that quoted an email or a rationale would leak it into a terminal log.

## 6. Input and output contracts

### 6.1 Oracle

`minor_units(amount)` returns `int(amount * 100)`. Amounts have at most two decimals by model validation.

`eligible_invoices(case)`: the case's invoices, in case order, with all of: `status == "open"`, `allocated_payment_id is None`, `currency == case.payment.currency`, `issue_date <= case.payment.date`.

`eligible_credits(case)`: the case's credits, in case order, with all of: `status == "valid"`, `consumed_by_payment_id is None`, `currency == case.payment.currency`.

`valid_allocations(case)` returns every triple `(customer_id, invoice_ids, credit_ids)` such that:

- the invoices are a non-empty set of eligible invoices of that one customer;
- the credits are a set, possibly empty, of eligible credits of the same customer, each linked (`credit.invoice_id`) to one of the chosen invoices;
- sum of invoice amounts minus sum of credit amounts equals the payment amount exactly.

`invoice_ids` and `credit_ids` are tuples in ascending ID order. The returned list is sorted. Each allocation appears once.

If any customer has more than `ORACLE_INVOICE_LIMIT` eligible invoices, it raises `OracleLimitExceeded(f"customer {customer_id} has {n} eligible invoices; the limit is {ORACLE_INVOICE_LIMIT}")`. Customers are visited in ascending ID order, so the first such customer is named.

### 6.2 `validate_case(case)`

Returns issues in the order of this table. Every issue has `case_id = case.case_id`.

| Code | Condition | Message |
| --- | --- | --- |
| `V101` | An ID is repeated within one record type. Types in this order: payment (target and related together), customer, invoice, credit, email. One issue per repeated ID, IDs ascending. | `duplicate <type> id <id>` |
| `V102` | `_validate_relationships(to_dataset(case))` raises `ValueError` | `str(error)` |
| `V103` | `case.payment.status != "unmatched"` or `case.payment.allocated_customer_id is not None` | `the target payment must be unmatched and unallocated` |
| `V201` | Decision is `allocate` and the label's customer is not among the case's customers | `label names unknown customer <id>` |
| `V201` | Decision is `allocate` and a labelled invoice is not among the case's invoices. One issue per ID, ascending. | `label names unknown invoice <id>` |
| `V201` | Decision is `allocate` and a labelled credit is not among the case's credits. One issue per ID, ascending. | `label names unknown credit <id>` |
| `V204` | `valid_allocations(case)` raises `OracleLimitExceeded` | `str(error)`. Return immediately after adding it. |
| `V202` | Decision is `allocate`, no `V201` was added, and `(customer_id, tuple(sorted(invoice_ids)), tuple(sorted(credit_ids)))` is not in the oracle's list | `the labelled allocation is not an exact, eligible allocation of this payment` |
| `V203` | `review_family == "ambiguous_allocation"` and the oracle found fewer than 2 | `ambiguous_allocation needs at least 2 exact allocations; found <n>` |
| `V203` | `review_family == "amount_mismatch"` and the oracle found at least 1 | `amount_mismatch needs 0 exact allocations; found <n>` |

The other six review families are not checked against the ledger. They are judgements about evidence.

### 6.3 `validate_seed(cases)`

`cases` are the cases of one seed. `seed_id = cases[0].seed_id`. Issues in this order:

1. Let `originals` be the case IDs with `variant.kind == "original"`, in input order. If `originals != [f"{seed_id}.original.0"]`: `Issue(seed_id, "V301", f"a seed needs exactly one original case with index 0; found {len(originals)}")`.
2. Then for each non-original case in input order, with `parent` looked up by `variant.parent_case_id` among `cases`:

| Code | Condition | Message |
| --- | --- | --- |
| `V302` | The parent is not among `cases`. Skip the other checks for this case. | `parent <parent_case_id> is not in this seed` |
| `V303` | Kind is in `LABEL_PRESERVING_KINDS` and the label shape differs from the parent's. Label shape is `(gold.decision, gold.review_family, len(gold.invoice_ids), len(gold.credit_ids))`. | `a <kind> variant must keep the decision, the review family and the size of the allocation` |
| `V304` | Kind is `twin` and `gold.decision == parent.gold.decision` | `a twin must have the opposite decision from its parent` |
| `V305` | Kind is in `PARAPHRASE_KINDS` and the two cases differ after text removal (below) | `a paraphrase may change only email subject, email body and the payment's remittance_reference` |
| `V306` | Kind is `human_paraphrase` and `author_id == parent.author_id` | `a human paraphrase must be written by a different author` |

Text removal: `case.model_dump(mode="json", exclude={"case_id", "variant", "author_id", "gold"})`, then set `payment.remittance_reference` to `""`, and every email's `subject` and `body` to `""`. Two cases with a different number of emails therefore differ.

The label shape compares sizes, not IDs, because a resample renames IDs.

### 6.4 `validate_cases(cases)` and `validate_tree(directory)`

`validate_cases`: `validate_case` for every case, then `validate_seed` for every seed in ascending seed ID. Returns all issues sorted (dataclass order: case ID, code, message).

`validate_tree(directory)`: for every `*.json` under the directory recursively, in sorted path order, with `label = path.relative_to(directory).as_posix()`:

| Situation | Issue | Then |
| --- | --- | --- |
| The file does not parse as JSON (`ValueError` from `json.loads`) | `Issue(label, "V001", "not valid JSON")` | Skip the file |
| `BenchCase.model_validate` raises `ValidationError` | One issue per entry of `error.errors()`: `Issue(label, "V001", f"{location}: {item['type']}")`, where `location` is the entry's `loc` parts joined with `.`, or `(case)` when `loc` is empty | Skip the file |
| The case ID was already seen in an earlier file | `Issue(label, "V002", f"case_id {case_id} is already used by {earlier_label}")` | Skip the file |

Catch `ValidationError` before `ValueError`: the first is a subclass of the second. The message uses the error type and location only. Never include `item["msg"]` or `item["input"]`: they can contain case text.

Returns `(number of cases loaded, number of distinct seeds among them, sorted(all issues))`, where all issues are the file issues plus `validate_cases(loaded cases)`.

### 6.5 Command

| Situation | Printed | Return |
| --- | --- | --- |

| Otherwise | One line per issue, `f"{case_id}\t{code}\t{message}"`, then `checked <cases> cases in <seeds> seeds: <n> issues` | 0 if no issue, else 1 |

## 8. Algorithm

Oracle, per customer, in integer minor units:

```
target        = minor_units(payment.amount)
invoices      = eligible invoices of this customer, ascending invoice_id
credits       = eligible credits of this customer whose invoice_id is one of `invoices`, ascending credit_id
credit_total  = sum of those credit amounts

walk(index, chosen, total):
    if total - credit_total > target: return            # no credit set can bring it back down
    if index == len(invoices):
        if chosen is empty or total < target: return
        usable = credits linked to a chosen invoice
        for each subset of `usable` whose amounts sum to (total - target):
            emit (customer_id, ids of chosen, ids of the subset)
        return
    walk(index + 1, chosen + [invoices[index]], total + amount(invoices[index]))
    walk(index + 1, chosen, total)
```

Credit subsets: depth-first over `usable` in order, adding a credit only if its amount is at most the amount still needed, emitting when the amount still needed is 0. When `total == target` this emits the empty set once.

The pruning step is sound because all amounts are positive. Worst case is exponential in the number of invoices. That is why the limit exists.

## 9. Edge cases and error handling

| Case | Required behaviour |
| --- | --- |
| An invoice issued after the payment date | Not eligible |
| A credit linked to an eligible invoice that is not chosen | Not usable for that allocation |
| A credit linked to an ineligible invoice | Never usable |
| Two credits of equal amount on one invoice, one needed | Two allocations, one per credit |
| A case with no eligible invoice at all | `valid_allocations` returns `[]` |
| `V204` | No `V202` or `V203` is reported for that case |
| A review label of a family other than the two checked ones | No ledger check |
| A directory with no JSON file | `(0, 0, [])`, command prints `checked 0 cases in 0 seeds: 0 issues` and returns 0 |
