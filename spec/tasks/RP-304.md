## 1. Objective and rationale

A comparison system: take a model's proposal and accept it whenever it is an exact, eligible allocation of the payment. No uniqueness check, no evidence check, no reading of any message.

Why it exists: it answers "what does basic validation buy". A reviewer will ask whether checking the arithmetic is enough. This baseline is that check and nothing more. On a case with two exact allocations it accepts whichever one the model named, which is exactly the failure the product's uniqueness rule prevents.

It is a baseline, not a product path. It lives in `backend/remitbench/` and uses the benchmark's own oracle.

## 3. Current behaviour and references

An investigator takes a `CandidateBundle` and returns an `InvestigationProposal` with `proposed_customer`, `invoice_ids` and `credit_ids`, or raises `InvestigatorError` (`backend/app/services/ai_investigator.py:24`). The bundle a model sees is the prompt view: `build_proof_set(payment, dataset).prompt_bundle` (`backend/app/services/proof_set.py`, RP-101). `valid_allocations(case)` is the benchmark oracle (RP-202). `allocate`, `review`, `System` and `SystemDecision` are in `backend/remitbench/systems.py` (RP-302).

## 6. Input and output contracts

`basic_validation(investigator)` returns a function of a case:

1. `bundle = build_proof_set(case.payment, to_dataset(case)).prompt_bundle`.
2. `proposal = investigator.investigate(bundle)`. On `InvestigatorError` return `review(case, "investigator_unavailable")`. No other exception is caught.
3. If `proposal.proposed_customer is None` or `proposal.invoice_ids` is empty: `review(case, "no_proposal")`.
4. `proposed = (proposal.proposed_customer, tuple(sorted(proposal.invoice_ids)), tuple(sorted(proposal.credit_ids)))`. If `proposed not in valid_allocations(case)`: `review(case, "not_an_exact_allocation")`.
5. Otherwise `allocate(case, *proposed)`.

The three reason strings are baseline reasons. They are not pipeline reasons and are not added to `ARCHITECTURE.md` section 5.

The investigator is called exactly once per case.

## 9. Edge cases and error handling

| Case | Required behaviour |
| --- | --- |
| The proposal is exact and the label is `review` | Allocated. That is the point of the baseline. |
| The proposal names an invoice that is not in the ledger | `not_an_exact_allocation` |
| The proposal's IDs are in another order | Same result |
| A ledger above the oracle's limit | `OracleLimitExceeded` propagates. A baseline run that cannot be checked stops. |
