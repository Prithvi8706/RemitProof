## 1. Objective and rationale

Create the package `backend/app/solver/` with two modules.

- `minor_units.py` converts a `Decimal` amount to an integer number of minor units (hundredths) and back. The conversion never rounds. An amount that is not a whole number of minor units is an error (DD-15).
- `problem.py` restates one payment's allocation search in integers. It turns a `CandidateBundle` into a `Problem`: one group per customer, one item per eligible invoice, one option per set of that invoice's eligible credits that fits the invoice.

Why: the solver of RP-502 works on integers only. Every rule about records (which invoice is eligible, which credit belongs to which invoice, how much credit an invoice can take) is settled here, once, so that the search itself contains no business rule. Eligibility is not restated: this task calls the two functions RP-102 made public, so the enumerator and the solver cannot drift apart.

Nothing consumes the new package in this task. No decision changes.

## 3. Current behaviour and references

The existing enumerator defines what a financially valid allocation is. Read it. Do not change it.

| Rule | Where |
| --- | --- |
| Eligible invoices: open, not allocated, payment currency, issued on or before the payment date, valid amount | `backend/app/services/alternative_finder.py:29` |
| Eligible credits: valid, not consumed, payment currency, valid amount | `backend/app/services/alternative_finder.py:44` |
| A payment whose amount is not a valid monetary amount has no allocation | `backend/app/services/alternative_finder.py:67` |
| Allocations are formed per customer: invoices of one customer, credits whose own `customer_id` is that customer | `backend/app/services/alternative_finder.py:77`, `:78` |
| A chosen credit must be linked (`invoice_id`) to a chosen invoice | `backend/app/services/alternative_finder.py:90` |
| For each chosen invoice, the chosen credits linked to it may total at most the invoice amount. Equal is allowed. | `backend/app/services/alternative_finder.py:18`, comparison at `:24` |
| A valid monetary amount is a finite, positive `Decimal` with at most two places | `backend/app/models/payment.py:13` |
| A bundle cannot hold two invoices, or two credits, with the same ID | `backend/app/models/investigation.py:81` |
| Money is quantized to two places | `backend/app/utils/money.py:11` |

Consequence used throughout Phase 5: because a credit only ever attaches to its own invoice and may not exceed it, an invoice together with a set of its credits contributes a net amount between zero and the invoice amount. That pair is an "option". Zero is possible (credits equal to the invoice).

The enumerator tries credit sets of size at most three per customer (`backend/app/services/alternative_finder.py:80`). This task does not copy that restriction. It builds every credit set that fits, up to a limit per invoice that the caller passes in.

## 6. Input and output contracts

### 6.1 `to_minor_units(amount)`

| Input | Result |
| --- | --- |
| Not a `Decimal` (including `int`, a binary floating-point number, `str`, `bool`, `None`) | `TypeError("amount must be a Decimal")` |
| `NaN`, `sNaN`, `Infinity`, `-Infinity` | `ValueError("amount must be finite")` |
| A finite `Decimal` that is not a whole number of hundredths | `ValueError(f"amount {amount} is not a whole number of minor units")` |
| Any other finite `Decimal` | The integer `amount * 100`, exact, with the sign of the amount |

The result is computed from `amount.as_tuple()` with integer arithmetic only. It must not use `Decimal` multiplication, division, `quantize`, `scaleb` or `int(amount * 100)`: each of those depends on the active decimal context and can round.

Before returning, the function checks `from_minor_units(result) == amount` and raises `ValueError(f"amount {amount} did not convert exactly")` otherwise. With a correct implementation this never fires. It is the assertion DD-15 asks for.

### 6.2 `from_minor_units(minor)`

| Input | Result |
| --- | --- |
| A `bool`, or anything that is not an `int` | `TypeError("minor must be an int")` |
| An `int` | The `Decimal` equal to `minor / 100` with exponent exactly -2, built with the tuple constructor `Decimal((sign, digits, -2))` |

`str(from_minor_units(1000000)) == "10000.00"`, `str(from_minor_units(5)) == "0.05"`, `str(from_minor_units(0)) == "0.00"`.

### 6.3 `build_problem(bundle, credit_limit)`

Evaluated in this order.

1. If `is_valid_monetary_amount(bundle.payment.amount)` is false, return `Problem(target=0, groups=())`. Nothing else is read.
2. `invoices = eligible_invoices(bundle)`, `credits = eligible_credits(bundle)`.
3. For each invoice, its linked credits are the eligible credits with `credit.customer_id == invoice.customer_id` and `credit.invoice_id == invoice.invoice_id`, sorted by `credit_id` ascending.
4. If an invoice has more than `credit_limit` linked credits, raise `ValueError(f"invoice {invoice.invoice_id} has {count} eligible credits; the limit is {credit_limit}")`. Invoices are visited in bundle order, so the first such invoice is named.
5. The item for an invoice: `invoice_id`, `amount = to_minor_units(invoice.amount)`, and `options` as in 6.4.
6. One `Group` per `customer_id` that has at least one item, in ascending `customer_id` order. Inside a group, items are sorted by amount descending, then `invoice_id` ascending.
7. `target = to_minor_units(bundle.payment.amount)`.

A credit that is eligible but linked to no eligible invoice of its own customer appears nowhere in the problem. That is the enumerator's behaviour too: such a credit can never be chosen.

### 6.4 Options of one item

One option for every subset of the item's linked credits, the empty subset included, whose amounts total at most the invoice amount:

- `credit_ids`: the subset's credit IDs as a tuple, ascending.
- `net`: invoice minor units minus the subset's total minor units.

Options are sorted by `credit_ids` (ordinary tuple comparison). The first option is therefore always `Option(net=amount, credit_ids=())`.

Guaranteed for every option: `0 <= net <= item.amount`. RP-502 relies on both ends.

## 8. Algorithm

```
to_minor_units(amount):
    sign, digits, exponent = amount.as_tuple()
    coefficient = the integer written by digits
    shift = exponent + 2
    if shift >= 0: magnitude = coefficient * 10**shift
    else:
        divisor = 10**(-shift)
        if coefficient % divisor != 0: error "not a whole number of minor units"
        magnitude = coefficient // divisor
    result = -magnitude if sign else magnitude
    check from_minor_units(result) == amount
    return result

options(amount, credits sorted by id):
    found = []
    extend(index, total, chosen):
        if index == len(credits): found.append(Option(amount - total, chosen)); return
        id, value = credits[index]
        if total + value <= amount: extend(index + 1, total + value, chosen + (id,))
        extend(index + 1, total, chosen)
    extend(0, 0, ())
    return found sorted by credit_ids
```

Cost of `options`: at most `2^c` leaves for `c` linked credits. Measured in the dry run for one invoice: 8 credits give 256 options in about 0.3 ms, 14 credits give 16,384 options in about 19 ms. The caller's `credit_limit` is what bounds this. RP-507 passes 8.

## 9. Edge cases and error handling

| Case | Required behaviour |
| --- | --- |
| `Decimal("7")`, `Decimal("7.5")`, `Decimal("10.000")`, `Decimal("1E+3")` | 700, 750, 1000, 100000 |
| `Decimal("-2.50")`, `Decimal("0.00")` | -250, 0. The conversion is general. Positivity is the eligibility rule's business. |
| An amount with 32 significant digits under a decimal context of precision 5 | Converts exactly and returns unchanged |
| A credit equal to its invoice | An option with `net == 0` |
| A credit larger than its invoice | No option contains it |
| Two credits that fit one at a time and not together | Two one-credit options, no two-credit option |
| A credit of customer B linked to an invoice of customer A | In no option |
| A credit linked to an ineligible or missing invoice | In no option |
| An ineligible credit on an invoice that is at the limit | Not counted toward the limit |
| No eligible invoice | `Problem(target=<payment minor units>, groups=())` |
| Payment amount `NaN` or with three decimal places (possible only through `model_copy` or `model_construct`) | `Problem(target=0, groups=())` |
| Two invoices with the same ID | Cannot occur: `CandidateBundle` rejects them. Test 19 pins that reliance. Not re-checked here. |
