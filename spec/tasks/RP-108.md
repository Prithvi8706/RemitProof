## 1. Objective and rationale

If any candidate email mentions an invoice or credit ID in a clause the reader could not classify, `process_payment` returns human review with reason `unread_instruction`, before the rules-only matcher and before the investigator.

Why: finding F2. The reader cannot read "This transfer settles INV_C", so today it treats the other sentence as the instruction and authorizes `INV_A` and `INV_B`. With this task the unread mention of `INV_C` blocks the payment.

This implements DD-07 in its strict form: any unread ID in any candidate email blocks. Two narrower rules were considered and rejected in the dry run:

- "Block only if the unread ID is part of a financially valid allocation." Rejected: an email that says the transfer clears an invoice which is not in any allocation (wrong amount, or unknown to the ledger) is exactly the case where the visible allocation is likely wrong. Test 6 pins this.
- "Block only for trusted senders." Rejected: an unreadable message about this payment is a reason for a person to look, whoever sent it. Test 7 pins this.

Trade-off, stated: the strict rule costs automation whenever a customer mentions any document in a sentence the reader does not know. On the legacy corpus the cost is zero (test 11). The real cost is measured in Phase 4.

## 6. Input and output contracts

### 6.1 `find_unread_instructions`

For each email in `bundle.candidate_emails`, in bundle order, compute `classify_document_semantics(f"{email.subject} {email.body}").unread_ids`.

- `email_ids`: the `email_id` of every email whose set is non-empty, in bundle order.
- `document_ids`: the union of those sets, sorted ascending.
- `blocks`: `bool(email_ids)`.

The function does not look at the sender, the email's customer, the alternatives or the payment.

### 6.2 `process_payment`

Directly after `proof_bundle = proof_set.proof_bundle`:

```
unread = find_unread_instructions(proof_bundle)
if unread.blocks:
    return ProcessingResult with
        baseline = BaselineResult(payment_id, status="unresolved", reason="unread_instruction")
        decision = Decision(
            payment_id, decision="human_review",
            proof={
                "unread_email_ids": list(unread.email_ids),
                "unread_document_ids": list(unread.document_ids),
                "investigator_skipped": True,
            },
            reason="unread_instruction", latency_ms=...)
        payment = payment.model_dump(mode="json")
        candidates = _candidate_dump(proof_bundle)
```

No other field of `ProcessingResult` is set. The investigator is not called. Use the constant `REASON_UNREAD_INSTRUCTION` for both reason values.

Resulting gate order: replay, incomplete search, unread instruction, rules-only matcher, payment status, investigator, proof and sufficiency.

## 9. Edge cases and error handling

| Case | Required behaviour |
| --- | --- |
| No candidate emails | Does not block |
| Unread ID belongs to no allocation, or to no record in the ledger | Blocks |
| Email from a sender that is not trusted | Blocks |
| Replayed payment with an unread email | Replay gate answers first |
| Search is `unknown` and an email is unread | `search_incomplete` answers first |
| A fully classified but misread sentence | Does not block. This is the F2 residual probe, which stays an expected failure. |
