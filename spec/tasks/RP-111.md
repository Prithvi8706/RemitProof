## 1. Objective and rationale

Three changes.

1. The audit script gains a third system, `cached_proposal_replay`: the 30 stored proposals in `results/proposal_cache.json` run through the current `process_payment`. The report moves to generation `v1` and is written to `audit/v1/`.
2. `audit/v0/` is kept byte for byte and pinned by hash in a test.
3. `docs/audit_v1.md` records the measured state after Phase 1. `docs/audit_baseline.md` gets one pointer paragraph.

Why: Phase 1 changed what gets authorized. The published snapshot in `results/` is a frozen input and still says 9 resolutions. Without a new report, nothing in the repository states what the changed pipeline does with the same proposals. The replay row is that statement, and it is reproducible by one command.

Why a new generation instead of editing v0: v0 is the reference every later comparison uses. A reference that changes is not a reference.

You copy the document text. You do not write it. Every sentence and number is supplied in section 6.

## 6. Input and output contracts

### 6.1 `load_cached_proposals(cache_path)`

Reads the file as UTF-8 JSON. For each value of `cache["entries"]`, in file order, validates `entry["proposal"]` with `InvestigationProposal.model_validate`. Returns a dictionary from `proposal.payment_id` to the proposal.

If two entries carry the same `payment_id`, raises `ValueError(f"two cached proposals for {proposal.payment_id}")`. Nothing else is caught: a missing file, invalid JSON or an invalid proposal raises whatever the library raises.

### 6.2 `proposals_sha256(proposals)`

`_sha256_json` of `{payment_id: proposals[payment_id].model_dump(mode="json") for payment_id in sorted(proposals)}`.

### 6.3 `CachedProposalInvestigator`

`__init__` stores the dictionary as `self.proposals`.

`investigate(bundle)` returns `self.proposals[bundle.payment.payment_id]` when the key is present. Otherwise it raises `InvestigatorError("no cached proposal for this payment")`.

### 6.4 `run_cases(dataset, ground_truth, cached_proposals)`

Everything RP-004 specified stays. In addition:

- Before the loop, create one `CachedProposalInvestigator(cached_proposals)`.
- For each payment, after the existing `process_payment` call, make a second call: `replay = process_payment(payment.payment_id, dataset, replay_investigator)`. Let `replay_auto = replay.decision.decision in {"matched_normally", "resolved"}`.
- Add three keys to the row, after `selected_credits`:

| Key | Value |
| --- | --- |
| `cached_proposal_replay_decision` | `"resolve"` if `replay_auto` else `"abstain"` |
| `cached_proposal_replay_correct_resolution` | `replay_auto and matches_truth(replay.decision.customer_id, replay.decision.invoice_ids, replay.decision.credit_ids, truth)` |
| `cached_proposal_replay_reason` | `None` if `replay_auto`, else `replay.decision.reason` |

`cached_proposal_replay_correct_resolution` must be a real boolean.

The fifteen existing row keys and their values do not change.

### 6.5 `build_report(dataset, ground_truth, cached_proposals)`

Passes `cached_proposals` to `run_cases`. The returned dictionary has the eight keys RP-004 specified plus two:

| Key | Value |
| --- | --- |
| `cached_proposal_count` | `len(cached_proposals)` |
| `cached_proposals_sha256` | `proposals_sha256(cached_proposals)` |

The `systems` value becomes exactly:

| Key | Value |
| --- | --- |
| `rules_only_baseline` | `"baseline_match over the complete proof set; no model"` |
| `verifier_only` | `"resolve only when exactly one financially valid allocation passes the existing proof and sufficiency checks; no model"` (unchanged) |
| `cached_proposal_replay` | `"process_payment with the stored proposals in results/proposal_cache.json; the model identity behind them is not verified"` |

The `rules_only_baseline` description changes because RP-103 changed what that path enumerates over.

# Audit record (v1): state after Phase 1

This file records the state of RemitProof after the Phase 1 soundness work. The v0 reference is `docs/audit_baseline.md`.

All figures are computed on the 80-receipt synthetic corpus in `data/`. That corpus is a regression fixture. It was written together with the verifier's lexical rules, so no figure here is evidence of how the system behaves on text it was not written against.

## What changed

| Finding | State at v0 | State at v1 |
| --- | --- | --- |
| F1. The model adds nothing on this corpus | Measured | Unchanged. Still true. |
| F2. An unread instruction could authorize the wrong invoices | 3 probes failing | Closed for the three recorded wordings. An email that names an invoice or credit in a clause the reader cannot classify sends the payment to review with reason `unread_instruction`. |
| F2 residual. A fully classified sentence that is classified wrongly | 1 probe failing | Open. Still 1 probe failing. Not addressed in Phase 1. |
| F3. Uniqueness was claimed on a truncated search | 2 probes failing | Closed. Uniqueness is decided over every ranked invoice and credit, not the capped prompt view. When retrieval drops an email or a strongly indicated customer, or a customer has more than 16 eligible invoices or more than 3 eligible credits, the answer is review with reason `search_incomplete`. |
| F4. Authorization depended on which customer was proposed | 2 probes failing | Closed. A payment resolves only if exactly one allocation is authorizable and the proposal names it. Otherwise the reason is `multiple_authorizable_allocations`. |

Two citation rules were removed from the gate: a selected credit no longer has to be repeated in the citation list, and an email from a trusted sender counts whether or not the proposal cited it.

## Measured figures

Scope: the 30 truth-labelled exceptions that the rules-only baseline does not resolve. 18 of them should be resolved. 12 should go to human review.

| System | Correct resolutions | Wrong automatic resolutions | Correct abstentions | False escalations |
| --- | --- | --- | --- | --- |
| Rules only | 0 | 0 | 12 | 18 |
| Model proposal alone (forced to answer) | 12 | 18 | 0 | 0 |
| Published pipeline at v0 (snapshot in `results/`, not regenerated) | 9 | 0 | 12 | 9 |
| Stored proposals replayed through the v1 pipeline | 12 | 0 | 12 | 6 |
| Verifier only: no model | 18 | 0 | 12 | 0 |

Sources: rows 2 and 3 are in `results/metrics.json`. Rows 1, 4 and 5 are in `audit/v1/verifier_only_baseline.json`, written by `backend/scripts/audit_baseline.py`.

Over all 80 receipts the v1 replay gives 50 normal matches, 12 resolutions and 18 reviews. At v0 it was 50, 9 and 21.

The three new resolutions are `PAY_057`, `PAY_063` and `PAY_068`. In each, the stored proposal already named the correct customer, invoices and credit. It was refused only because it did not repeat the credit in its citation list.

The six remaining false escalations are `PAY_053`, `PAY_064`, `PAY_066`, `PAY_072`, `PAY_078` and `PAY_080`. In each, the stored proposal names a customer, an invoice set or a credit set that differs from the truth label, and the checks refuse it. The verifier-only system resolves all six correctly.

## How much this shows

Uncertainty: 0 wrong in 12 automatic resolutions gives a one-sided 95% upper bound of 22.1% on the wrong-resolution rate. 12 correct in 18 gives a 95% Wilson interval of 43.7% to 83.7% on coverage. For the verifier-only system, 0 wrong in 18 gives an upper bound of 15.3%.

The move from 9 to 12 is three payments on one fixture. The v0 interval (29.0% to 71.0%) and the v1 interval overlap. It is not evidence of a general improvement.

The stored proposals come from a model whose identity is not verified.

The new rules cost nothing on this corpus: no legacy email contains an unread ID, no legacy payment has an incomplete search, and no legacy payment has two authorizable allocations. Their cost on other text is not measured here.

## What this record does not show

- Behaviour on remittance text written by anyone other than the author of the verifier.
- Behaviour with a live model. No identity-verified model run is recorded.
- Behaviour on ledgers where payments share customers. No two payments in the corpus do.
- How often the unread-instruction rule sends a readable, harmless email to review.
- Anything about a sentence the reader classifies with confidence and gets wrong.

## 8. Algorithm

`run_cases`, per payment:

```
result  = process_payment(payment_id, dataset, verifier_only_investigator)     # as before
replay  = process_payment(payment_id, dataset, replay_investigator)            # new
row     = the fifteen existing keys from `result` and `outcome`, unchanged
row    += the three replay keys from `replay`
```

The two calls are independent. `process_payment` does not change the dataset. Do not reuse `result` for the replay keys.

Cost: 160 pipeline calls for the legacy corpus. Observed run time of the script: under 10 seconds.

## 9. Edge cases and error handling

| Case | Required behaviour |
| --- | --- |
| A payment has no stored proposal | `CachedProposalInvestigator.investigate` raises `InvestigatorError`. `process_payment` returns human review. The row gets `"abstain"` and the pipeline's reason string. Not an error. |
| A payment is resolved by the rules-only path | The investigator is not called. `replay_auto` is true through `matched_normally`. Such rows are outside the comparison scope and do not appear in `cases`. |
| Two cache entries for one payment | `ValueError` from `load_cached_proposals`, message per 6.1. The script exits with a traceback. Not caught. |
| `--cache` points to a missing file | `FileNotFoundError`. Not caught. |
| `audit/v1/verifier_only_baseline.json` already exists when you run `--write` | The script refuses. Stop: the start state was wrong. |
| The v0 report has CRLF line endings on your machine | The pinning test normalizes `b"\r\n"` to `b"\n"` before hashing. Do not convert the file. |
