## 1. Objective and rationale

`search` stops calling the exhaustive enumerator and calls the solver of RP-501 to RP-504. Four limits bound it:

| Constant | Value | Was | Meaning |
| --- | --- | --- | --- |
| `INVOICE_SEARCH_LIMIT` | 64 | 16 | Eligible invoices per customer |
| `CREDITS_PER_INVOICE_LIMIT` | 8 | `CREDIT_SEARCH_LIMIT = 3`, per customer | Eligible credits linked to one eligible invoice |
| `ALTERNATIVE_LIMIT` | 2048 | none | Allocations returned |
| `NODE_BUDGET` | 2000000 | none | Search nodes per call |

Going over any of them gives `unknown`, never a shortened answer (INV-06, INV-12).

Why each value. All four were decided in the dry run.

- **64 invoices.** Recorded in DD-06. The solver's recursion is one level per invoice, and the node budget bounds the work whatever the size.
- **Credits: per invoice, 8.** The old limit of 3 per customer existed only because the enumerator never combines more than three credits (`backend/app/services/alternative_finder.py:80`). The solver has no such restriction, so the reason for a per-customer limit is gone. What does grow is the number of options of one invoice: it doubles with each credit linked to it. Measured: 8 credits give 256 options in 0.2 ms per invoice, 14 give 16,384 in 18 ms. Eight is the last step where 64 such invoices still build in about 15 ms.
- **2048 allocations.** Every later stage needs the whole list, not a count. The rules-only matcher filters it by customer and by referenced invoice IDs before it counts (`backend/app/services/baseline_matcher.py:93`, `:142`, `:151`). The gate counts how many alternatives the evidence supports (`backend/app/services/evidence_sufficiency.py:108`). Authorization tests every alternative (`backend/app/services/authorization.py:49`), and its cost grows with the square of the list: measured 1.3 s at 210 alternatives and 6.7 s at 495. So the list must be complete or refused, and it must be bounded. The bound is the smallest power of two above what a ledger the sandbox accepts can ever produce: 8 invoices and 3 credits allow at most 255 invoice sets times 8 credit sets, 2040. With 2048 no sandbox request can be refused for this reason (DD-24). The largest count the dry run found on such a ledger is 266.
- **2,000,000 nodes.** A search that runs out stops after 0.32 to 0.34 s on Python 3.13.18 and 0.46 to 0.49 s on Python 3.9.25 on the dry-run machine (one core of a 2.3 GHz Xeon). The budget counts nodes, so the outcome for a ledger is the same on every machine. Only the time differs.

What this does not achieve. The limit of 64 is real for payments that cover one or two invoices and mostly nominal beyond that: RP-508 measures that 241 of 360 synthetic 64-invoice ledgers still end `unknown`. That is a refusal, so it is safe. It is stated here so that nobody reads "64" as "solved up to 64".

The plan had this task at 2 hours. It is 4: five existing tests pin the old limits and are revised by name, and the cap on the list was not in the scope statement.

## 6. Input and output contracts

### 6.1 `search`

Evaluated in this order. The first matching row decides.

| # | Condition | `status` | `complete` | `alternatives` | `detail` | `incomplete_reasons` |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | `proof_set.complete` is false | `unknown` | `False` | `()` | `retrieval_incomplete` | `proof_set.incomplete_reasons` |
| 2 | Some customer has more than 64 eligible invoices in the proof bundle | `unknown` | `False` | `()` | `invoice_limit` | `()` |
| 3 | Some eligible invoice has more than 8 linked eligible credits | `unknown` | `False` | `()` | `credit_limit` | `()` |
| 4 | The solver stops with status `node_budget` | `unknown` | `False` | `()` | `node_budget` | `()` |
| 5 | The solver stops with status `solution_limit` | `unknown` | `False` | `()` | `alternative_limit` | `()` |
| 6 | The solver completes with no allocation | `none` | `True` | `()` | `None` | `()` |
| 7 | The solver completes with exactly one | `unique` | `True` | that one | `None` | `()` |
| 8 | The solver completes with two or more | `ambiguous` | `True` | all, in solver order | `None` | `()` |

Rows 1 to 3 must call neither `build_problem` nor `solve`. Rows 4 to 8 call `build_problem(bundle, CREDITS_PER_INVOICE_LIMIT)` once and `solve(problem, solution_limit=ALTERNATIVE_LIMIT + 1, node_budget=NODE_BUDGET)` once. The four constants are read from the module at call time, so that a test can replace them.

Row 3, exactly: a credit is counted for the pair `(credit.customer_id, credit.invoice_id)` when it is in `eligible_credits(bundle)` and that pair is the `(customer_id, invoice_id)` of an invoice in `eligible_invoices(bundle)`. This is the same rule `build_problem` uses to link credits (RP-501, section 6.3). A credit linked to an ineligible or missing invoice, or belonging to another customer than its invoice, is not counted.

Rows 4 and 5 return no allocation, even though the solver found some. A list that may be incomplete must not reach a caller.

Why the solver is asked for one more than the limit: with a limit of `k` the solver reports `solution_limit` on finding the `k`-th allocation and cannot say whether more exist (RP-503, section 6.1). Asking for 2049 means a `complete` answer can hold up to 2048, and 2049 found means "more than the limit".

### 6.2 The alternatives

## 8. Algorithm

```
search(proof_set):
    if not proof_set.complete: return unknown("retrieval_incomplete", reasons)
    bundle = proof_set.proof_bundle
    invoices = eligible_invoices(bundle)
    if any customer has more than INVOICE_SEARCH_LIMIT of them: return unknown("invoice_limit")
    pairs = {(invoice.customer_id, invoice.invoice_id) for invoice in invoices}
    count eligible credits per (credit.customer_id, credit.invoice_id), only for pairs in `pairs`
    if any count is above CREDITS_PER_INVOICE_LIMIT: return unknown("credit_limit")
    problem = build_problem(bundle, CREDITS_PER_INVOICE_LIMIT)
    result = solve(problem, solution_limit=ALTERNATIVE_LIMIT + 1, node_budget=NODE_BUDGET)
    if result.status == "node_budget": return unknown("node_budget")
    if result.status == "solution_limit": return unknown("alternative_limit")
    alternatives = one AlternativeAllocation per solution, per 6.2
    status = "none", "unique" or "ambiguous" for 0, 1 or more
    return SearchOutcome(status, True, alternatives, None, ())
```

Why the budget cannot be reached inside the old limits. Without any pruning the search visits, level by level, the product of "options plus one" of the items above. For 16 items and 3 credits the largest such tree is the one where all three credits sit on the first item (8 options, 9 branches): `1 + 9 * (2^16 - 1) = 589,816` nodes. That is below 2,000,000. So every ledger the old search accepted is searched to the end, and the only new refusal inside the old limits is row 5.

## 9. Edge cases and error handling

| Case | Required behaviour |
| --- | --- |
| Payment amount is not a valid monetary amount | `build_problem` returns the empty problem, the solver returns no allocation, the status is `none`. As before. |
| 65 invoices for one customer, one of them paid | 64 eligible: searched |
| 64 eligible invoices for each of two customers | Searched. The limit is per customer. One node budget covers both. |
| Eight credits on each of two invoices of one customer | Searched. The limit is per invoice. |
| Nine credits on a paid invoice, or on an invoice ID that does not exist | Not counted. Searched. |
| A ledger with exactly `ALTERNATIVE_LIMIT` allocations | `ambiguous`, complete |
| `build_problem` raises `ValueError` although row 3 passed | Not caught. Rows 3 and `build_problem` count by the same rule, so this cannot happen. If it does, it is a defect, and an exception never produces an automatic decision (INV-10). |
| More than 999 allocations | The IDs go on as `ALT_1000` and upward, as the enumerator's format did |
