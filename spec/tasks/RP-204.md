## 1. Objective and rationale

Two functions: one turns a benchmark case into the `Dataset` the pipeline takes, one runs the pipeline on the case's payment.

Why a separate module: this is the only place where a case crosses into runtime code. The gold label must not cross with it. Keeping the crossing in one small file makes that checkable by reading.

This task runs second in Phase 2, before RP-202, because the validator needs `to_dataset`.

## 3. Current behaviour and references

`Dataset` is a dataclass with the fields `payments`, `invoices`, `customers`, `credits`, `emails`, in that order (`backend/app/utils/loaders.py:17-22`).

The sandbox builds one the same way: the target payment first, then related payments (`backend/app/api/sandbox.py:46-50`). Do not import the sandbox.

`process_payment(payment_id, dataset, investigator)` is the single runtime entry point (`backend/app/services/pipeline.py:40`). The `Investigator` protocol is in the same file (`backend/app/services/pipeline.py:26`, audited line numbers; Phase 1 inserted imports above them).

## 5. Interfaces

```python
def to_dataset(case: BenchCase) -> Dataset
def run_case(case: BenchCase, investigator: Investigator) -> ProcessingResult
```

Imports: `ProcessingResult` from `app.models`; `Investigator` and `process_payment` from `app.services.pipeline`; `Dataset` from `app.utils.loaders`; `BenchCase` from `remitbench.schema`. Nothing else.

Module docstring, exactly: `"""Turns a benchmark case into pipeline input. The gold label never crosses this boundary."""`

## 6. Input and output contracts

`to_dataset(case)` returns

```python
Dataset(
    payments=[case.payment, *case.related_payments],
    invoices=list(case.invoices),
    customers=list(case.customers),
    credits=list(case.credits),
    emails=list(case.emails),
)
```

The lists are new list objects. The record objects inside them are the case's own objects. It does not validate anything and does not read `case.gold`, `case.variant`, `case.author_id`, `case.seed_id` or `case.case_id`.

`run_case(case, investigator)` returns `process_payment(case.payment.payment_id, to_dataset(case), investigator)`. It catches nothing.

Neither function has any other statement.

## 9. Edge cases and error handling

| Case | Required behaviour |
| --- | --- |
| A case whose records are inconsistent, for example an invoice of an unknown customer | `to_dataset` still returns a `Dataset`. Consistency is the validator's job (RP-202). |
| A related payment that is a replay of the target payment | Passed through. The pipeline's replay gate decides. |
| The investigator raises `InvestigatorError` | `process_payment` handles it and returns human review. `run_case` adds nothing. |

## 12. Tests

All in `backend/tests/test_remitbench_adapter.py`. 5 test functions, 11 collected tests. `EXAMPLES = Path(__file__).resolve().parents[2] / "bench" / "examples"`. A local class `NoProposal` whose `investigate(self, bundle)` raises `InvestigatorError("no proposal in this test")`.

| # | Name | Kind | Arrange and act | Assert |
| --- | --- | --- | --- | --- |
| 1 | `test_dataset_holds_every_record_and_the_target_payment_first` | Unit, parametrized over `EX01`, `EX02`, `EX03` | `dataset = to_dataset(load_case(...))` | `isinstance(dataset, Dataset)`; `dataset.payments[0] == case.payment`; `dataset.invoices`, `.customers`, `.credits`, `.emails` equal the case's lists |
| 2 | `test_related_payments_follow_the_target_payment` | Unit | Copy EX02's payment with `payment_id="RCPT-EARLIER"` and `bank_reference="IMPS-1"`; copy the case with `related_payments=[that]` | Payment IDs of the dataset are `["RCPT-EX02", "RCPT-EARLIER"]` |
| 3 | `test_dataset_lists_are_copies` | Unit | `dataset = to_dataset(EX01)`; clear `dataset.invoices` and `dataset.emails` | `len(case.invoices) == 3` and `len(case.emails) == 1` |
| 4 | `test_no_part_of_the_gold_label_reaches_the_dataset` | Boundary, parametrized over the three examples | `dumped = repr(to_dataset(case))` | `not hasattr(dataset, "gold")`; `case.gold.rationale not in dumped`; `"review_family" not in dumped` |
| 5 | `test_run_case_is_process_payment_on_the_target_payment` | Integration, parametrized over the three examples | `result = run_case(case, NoProposal())`; `direct = process_payment(case.payment.payment_id, to_dataset(case), NoProposal())` | `result.payment["payment_id"] == case.payment.payment_id`; `result.decision.decision` is one of `matched_normally`, `resolved`, `human_review`; `result.decision.model_dump(exclude={"latency_ms"})` equals the same dump of `direct.decision` |

Test 5 does not pin which decision the pipeline makes on an example. That will change when the reader changes in Phase 4, and it must not break this test.
