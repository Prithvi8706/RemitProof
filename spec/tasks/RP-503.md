## 1. Objective and rationale

Give `solve` an optional `solution_limit`. With a limit of `k` the search stops the moment it has found `k` allocations and says so with a second status, `solution_limit`.

Why: two different callers need two different answers.

- "Is there more than one allocation?" needs the search to stop at the second (DD-16). That is `solution_limit=2`. The comparison with CP-SAT (RP-506) uses it.
- The pipeline needs the full list. The dry run for this phase checked every consumer of `SearchOutcome.alternatives`. The rules-only matcher filters the list by customer and by referenced invoice IDs before it counts (`backend/app/services/baseline_matcher.py:93`, `:142`, `:151`). The sufficiency gate counts how many alternatives the evidence supports (`backend/app/services/evidence_sufficiency.py:108`, `:128`). Authorization tests every alternative (`backend/app/services/authorization.py:49`). Each of them can read "exactly one" out of a list of two that is missing a third. So `search` (RP-507) asks for the full list up to a cap, and treats a stop at the cap as `unknown`.

The plan had "credit options" under this ID. RP-501 and RP-502 already cover credits, so the ID is reused.

This task changes one function. Nothing consumes the solver yet. No decision changes.

`solve(problem)` (RP-502) always runs to the end and always returns status `complete`. Its search order is fixed by section 8.1 of the RP-502 contract: groups in order, and at each item the options in order, then skip. The k-th allocation found is therefore the same on every run and every Python version.

## 6. Input and output contracts

### 6.1 `solve(problem, solution_limit)`

Argument checks, in this order:

1. `solution_limit` is not `None` and is below 1: `ValueError("solution_limit must be at least 1")`.
2. The RP-502 check: groups present and `target < 1`: `ValueError("target must be at least 1")`.

Result:

| Situation | `status` | `solutions` | `nodes` |
| --- | --- | --- | --- |
| `solution_limit` is `None` | As in RP-502 | As in RP-502 | As in RP-502 |
| The search ends by itself having found fewer than `solution_limit` allocations | `complete` | Every allocation | Every node |
| The search finds its `solution_limit`-th allocation | `solution_limit` | Exactly `solution_limit` allocations: the first found in search order, returned sorted ascending | The nodes visited up to and including the node that recorded the last one |

What each status means, and nothing more:

- `complete`: the list is every allocation that exists.
- `solution_limit`: at least this many allocations exist. Whether more exist is not known. This holds even when the stop happened at what would have been the last node: the search did not look further, so it cannot say.

The limit counts allocations across all groups. A stop ends the whole call, not one group.

## 7. Implementation steps

1. Add the constant, the exception class and the parameter.
2. Wrap the loop over groups in one `try`. Directly after an allocation is recorded, if `solution_limit` is not `None` and the number of recorded allocations is at least `solution_limit`, raise `_Stop`. The single `except _Stop` around the loop sets the status to `solution_limit`.
3. Create the tests in section 12.
4. Run section 13.

## 8. Algorithm

Only the end-of-list branch of `visit` changes:

```
if i == n:
    record the allocation
    if solution_limit is not None and len(solutions) >= solution_limit:
        raise _Stop
    return
```

and around the whole search:

```
status = "complete"
try:
    for each group: visit(0, 0)
except _Stop:
    status = "solution_limit"
return SolveResult(status, sorted(solutions), nodes)
```

Why stopping early cannot produce a wrong allocation: recording is unchanged, so every entry in the list is an exact allocation by the argument of RP-502 section 8.5. The stop only makes the list shorter. The only new risk is the status, and it is set in exactly one place.

Worked example, continued from RP-502 section 8.6 (items 700, 500, 300, 200, target 1000, 15 nodes without a limit):

| `solution_limit` | Stops at node | Status | Allocations returned |
| --- | --- | --- | --- |
| 1 | 7 | `solution_limit` | `INV_A` with `INV_C` |
| 2 | 12 | `solution_limit` | Both |
| 3 | Never (15 nodes) | `complete` | Both |

With a limit of 2 the search stops three nodes before the end and reports `solution_limit`, although the complete search would have found nothing more. That is the intended reading: a caller that wants to know there are exactly two must ask for three.

## 9. Edge cases and error handling

| Case | Required behaviour |
| --- | --- |
| No allocation exists, any limit | `complete`, empty list, same node count as without a limit |
| The first group alone reaches the limit | Later groups are not searched |
| Allocations found in an order that is not ascending | The returned tuple is sorted all the same |
| `solution_limit=0` or negative | `ValueError`, before anything is searched |
