## 1. Objective and rationale

Add property tests that generate small ledgers and compare `search` with a brute-force oracle written from the definition of a financially valid allocation, sharing no code with the enumerator.

Why: the example tests of RP-101 to RP-104 pin a handful of hand-built ledgers. They cannot show that "unique" means unique for ledgers nobody thought of. Four properties are checked on 300 generated ledgers each:

1. Over the proof bundle, the search returns exactly the oracle's allocations, and its status matches their number.
2. For every candidate customer, every allocation the oracle finds over the customer's whole ledger is in the search result. This is the completeness claim that RP-101 exists for.
3. The prompt view never contains an allocation the search lacks (DD-04).
4. The result does not depend on the order of records in the dataset.

## 3. Current behaviour and references

Definition of a financially valid allocation for a payment, as implemented by `find_valid_alternatives` (`backend/app/services/alternative_finder.py:29`) and as the oracle must restate it independently:

- One customer.
- A non-empty set of that customer's invoices, each open, with no `allocated_payment_id`, in the payment currency, and with `issue_date <= payment.date`.
- A possibly empty set of that customer's credits, each with status `valid`, no `consumed_by_payment_id`, in the payment currency, and linked (`invoice_id`) to one of the chosen invoices.
- For each chosen invoice, the sum of the chosen credits linked to it does not exceed the invoice amount.
- Sum of invoice amounts minus sum of credit amounts equals the payment amount exactly.

Read `alternative_finder.py` to understand it. Do not import any private name from it into the test, and do not call `money_sum` in the oracle.

## 6. Input and output contracts

### 6.1 `oracle`

Works in integer cents: `int(amount * 100)`. For each customer ID that owns at least one given invoice, in ascending order:

1. `open_invoices`: that customer's invoices that pass the four invoice conditions of section 3, in the given order.
2. `usable_credits`: that customer's credits that pass the three credit conditions (status, not consumed, currency), in the given order.
3. For every non-zero bit mask over `open_invoices` and every bit mask (including zero) over `usable_credits`:
   - skip if a chosen credit's `invoice_id` is not a chosen invoice;
   - skip if, for any chosen invoice, the cents of chosen credits linked to it exceed the invoice's cents;
   - skip if invoice cents minus credit cents differs from the payment cents;
   - otherwise add `(customer_id, frozenset(invoice IDs), frozenset(credit IDs))`.

Returns the set.

### 6.2 `ledgers`

A composite strategy that returns a `Dataset` with one payment, both customers, no emails. Draws, in this order:

1. For `(CUS_1, at most 10 invoices)` then `(CUS_2, at most 4 invoices)`:
   - the number of invoices, an integer from 0 to the maximum;
   - for each invoice with index `i`: ID `INV_<last character of the customer ID><i>` (for example `INV_13`); `amount` sampled from `INVOICE_AMOUNTS`; `currency` sampled from `["USD", "USD", "USD", "USD", "EUR"]`; `issue_date` sampled from `[date(2026, 6, 16)] * 3 + [date(2026, 9, 1)]`; `due_date=date(2026, 7, 16)`; `description="Services"`; `status` sampled from `["open", "open", "open", "open", "paid"]`;
   - if the customer has at least one invoice: the number of credits, an integer from 0 to 3; for each credit with index `i`: ID `CR_<last character><i>`; `invoice_id` of an invoice sampled from this customer's invoices; `amount` sampled from `CREDIT_AMOUNTS`; `currency="USD"`; `reason="Rebate"`; `status` sampled from `["valid", "valid", "valid", "invalid"]`.
2. The payment amount: sampled from `["500.00", "1000.00", "1500.00", "2100.00"]`.
3. If `CUS_1` has at least one invoice, draw a boolean. If it is true: draw a list of 1 to 4 distinct `CUS_1` invoices; if any credit is linked to one of them, draw a list of 0 to 3 distinct such credits (otherwise the empty list); compute the net of the drawn invoices minus the drawn credits; if the net is positive, it replaces the payment amount.
4. `remittance_reference`: sampled from `["", "", <ID of the first invoice in the ledger, or "" if there is none>]`.

Payment: `payment_id="PAY_1"`, `date=PAYMENT_DATE`, `currency="USD"`, `payer_name="Acme Trading Ltd"`, `bank_reference="BNK-1"`.

Why these choices: ten invoices for one customer exceed the prompt cap of eight, so property 2 is exercised. Amounts come from a small set so that different subsets often have equal sums. Step 3 makes payments that match a subset with credits, including credits larger than their invoice.

### 6.3 `_outcome`

`proof_set = build_proof_set(dataset.payments[0], dataset)`; returns `(proof_set, search(proof_set))`.

## 8. Algorithm

`oracle` cost per example: at most `2^10` invoice masks times `2^3` credit masks for `CUS_1`. Measured: the whole file runs in about 7 seconds on Python 3.13 and 11 seconds on Python 3.9.

## 9. Edge cases and error handling

| Case | Required behaviour |
| --- | --- |
| A generated ledger has no invoices | Valid example. The oracle returns the empty set and the status is `none`. |
| A property fails | Hypothesis prints a minimal failing ledger. Copy it into the report. Do not change the generator, the oracle, the settings or application code to make it pass. |
| The search status is `unknown` for a generated ledger | Property 1 asserts this never happens with this generator (at most 10 invoices and 3 credits per customer, no emails). A failure here is a finding. |
