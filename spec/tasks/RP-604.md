## 1. Objective and rationale

Add one test file with 52 tests. Forty pass and pin what document text, payment fields and proposals cannot do (INV-09, INV-04, INV-02). Twelve are strict expected failures. They record three findings of the hostile-input review, in the way RP-002 recorded F1 to F4.

The plan had this task as "hostile-input tests, 3 hours, low risk". It is larger because the review found unsafe behaviour. The findings, each observed on the tree after RP-601:

| ID | Finding | Example | What the system does today |
| --- | --- | --- | --- |
| F5 | A remittance instruction that the reader reads completely, and that names other invoices than the only exact allocation, does not stop the rules-only match. | Payment 10000.00. Open invoices `INV_A` 6000.00 and `INV_C` 10000.00. The customer writes "Apply BNK-1 only to INV_A." | `matched_normally` on `INV_C` |
| F6 | An identifier is recognised only as `INV_`, `CR_` or `EMAIL_` followed by letters and digits. A prohibition that spells it another way is not seen. | "Do not apply this payment to INV-C." Also `INV C`, `INVC`, full-width letters, a zero-width character inside the identifier. | `matched_normally` on `INV_C` |
| F7 | A hold that names no identifier is not read. | "Do not apply this payment to any invoice." "This payment was sent in error. Please refund it." | `matched_normally` on `INV_C` |

Why the audit and Phase 1 did not see them: in the legacy corpus none of the 50 matched payments has a candidate email at all, so the rules-only path never meets an instruction there.

Why the cause of F5 is narrow: the matcher reads affirmative invoice IDs only from the payment's own reference fields (`backend/app/services/baseline_matcher.py:99`). From emails it uses prohibitions and credit instructions (`:105` onward) and ignores affirmative invoice IDs. The proof engine does hold such an instruction against a proposal (`backend/app/services/proof_engine.py:393`). So the two automatic paths disagree.

What happens to each finding:

| ID | Handling |
| --- | --- |
| F5 | Fixed by RP-606, the next task. RP-606 removes the three F5 markers. |
| F6 | Recorded. DD-19 (identifiers resolve against the ledger) is the designed answer and belongs to Phase 4. The markers stay until a Phase 4 contract names them. |
| F7 | Recorded. Whether text the reader cannot classify should block is the question the Phase 4 reading policies measure (DD-18). The markers stay until a Phase 4 contract names them, or the owner accepts F7 as a stated limit. |

Owner: F6 and F7 mean that until Phase 4 the rules-only path can apply a payment against a customer's written wish when the wish is not phrased in the reader's patterns. Nothing in this task changes that. It makes it visible and keeps the suite red-proof against a silent change.

## 6. Input and output contracts

| Helper | Contract |
| --- | --- |
| `_invoice` | Currency `USD`, issue date 2026-06-16, due date 2026-07-16, description `Services`, `Decimal(amount)` |
| `_payment` | `PAY_1`, 2026-08-10, `10000.00` `USD`, payer `Acme Trading Ltd`, bank reference `BNK-1`. Keyword arguments replace fields. |
| `_email` | `EMAIL_1`, the sender and customer given, date 2026-08-09, subject `Remittance BNK-1` |
| `_unique` | `INV_A` 6000.00 and `INV_C` 10000.00, both `CUS_1`. One exact allocation: `INV_C`. |
| `_two` | `INV_A` 6000.00, `INV_B` 4000.00, `INV_C` 10000.00. Two exact allocations. |
| `_dataset` | One payment (`_payment()` unless given), the invoices, the customers, no credits, the emails |
| `_decision` | `process_payment("PAY_1", dataset, investigator).decision`, with `Unavailable()` when the proposal is `None` and `Fixed(proposal)` otherwise |
| `_all_decisions` | A list: first `_decision(dataset)`, then, for each alternative of `search(build_proof_set(payment, dataset))` in order, `_decision(dataset, canonical_proposal(proof_bundle, alternative))` |
| `_summary` | `(decision.decision, decision.customer_id, sorted invoice IDs as a tuple, sorted credit IDs as a tuple)` |
| `_proposal` | Defaults `payment_id="PAY_1"`, `proposed_customer="CUS_1"`, `invoice_ids=["INV_C"]`, `evidence_ids=["CUS_1"]`. Keyword arguments replace fields. |

`_all_decisions` is the tool against "the right proposal would have got through": it asks for the decision with no proposal and with the best-formed proposal for every allocation that exists.
