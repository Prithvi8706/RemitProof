## 1. Objective and rationale

`backend/remitbench/expand.py` produces up to six variants of each seed, and a command writes them to a directory.

| Kind and index | Operator | What it does | Label |
| --- | --- | --- | --- |
| `resample` 0, 1, 2 | `resample_ids` | Renames every record ID that contains a digit, everywhere | Same decision; IDs renamed |
| `noise` 0 | `noise_reorder` | Changes the order of the record lists | Unchanged |
| `noise` 1 | `noise_distractors` | Adds eight open invoices that are too large to take part in any exact allocation, then reorders | Unchanged |
| `twin` 0 | `twin_no_remittance` or `twin_competitor` | Only for `allocate` seeds. Removes every message from the customer. If fewer than two exact allocations remain, adds a competing one. | `review`, `ambiguous_allocation` |

Why these and no others: each can be argued without judgement.

- Renaming is an isomorphism. It is skipped when a message shortens an ID, because then renaming would break the message.
- Order carries no meaning in a ledger.
- An invoice larger than the payment plus every usable credit cannot be part of an exact allocation. The guide's rule 1 (exact amounts only) makes it inert.
- With no message from the customer and at least two exact allocations, the guide's rule 3 (no default habits) makes the answer `review`.

What this task deliberately does not do: change amounts, names or dates; add typos; rewrite text. Each of those can change what a human would decide. Text variation comes from human and model paraphrases (H-204), which are files, not code.

Determinism: no use of the `random` module. Every draw is a SHA-256 of a key string. The same seeds and the same generator seed give the same bytes on every Python version.

## 6. Input and output contracts

Throughout, `S` is the generator seed and string keys are built with f-strings exactly as written. A key that differs by one character gives different output.

### 6.1 Building blocks

`draw(key, bound)`: `int.from_bytes(hashlib.sha256(key.encode("utf-8")).digest()[:8], "big") % bound`.

`_token_pattern(values)`: a compiled regular expression that matches any of the values as a whole token. Deduplicate the values, order them by length descending and then alphabetically, escape each with `re.escape`, join with `|`, and wrap as `(?<![A-Za-z0-9])(?:...)(?![A-Za-z0-9])`. Longest first, so that an ID is never matched as a part of a longer ID.

`record_ids(case)`: a list in this order: the target payment ID; related payment IDs; customer IDs; invoice IDs; credit IDs; email IDs. Each group in case order.

`text_fields(case)`: a list in this order: target payment `remittance_reference`, then `bank_reference`; for each related payment the same two; every invoice `description`; every credit `reason`; for each email `subject`, then `body`.

`fragments(record_id)`: the maximal runs matching `[A-Za-z0-9]+` in the ID, in order, kept when the run has at least 3 characters and contains at least one digit.

`has_partial_mentions(case)`: let `ids = record_ids(case)` and `pieces` = sorted set of all fragments of all IDs, minus anything that is itself an ID. If `pieces` is empty return `False`. Otherwise, for each text field: replace every whole-token occurrence of an ID with one space, then search for a whole-token occurrence of a piece. Return `True` if any field has one.

### 6.2 `rename_map(case, key)` and `apply_rename(case, mapping)`

`rename_map`: start with `taken` = the case-folded set of all record IDs. For each ID in `record_ids` order: skip it if it has no digit. Otherwise, with `attempt` starting at 0, build a candidate by replacing each digit character at string position `position` with `str(draw(f"{key}:{old}:{attempt}:{position}", 10))` and keeping every other character. If the case-folded candidate is in `taken`, add 1 to `attempt` and build again. Otherwise add it to `taken` and map the old ID to it.

`apply_rename` works on `case.model_dump(mode="json")` and returns the dictionary. With an empty mapping it returns the dump unchanged. Otherwise, with `pattern = _token_pattern(list(mapping))`:

- Identifier fields are replaced by exact lookup (`mapping.get(value, value)`, `None` stays `None`): every payment's `payment_id` and `allocated_customer_id`; customer `customer_id`; invoice `invoice_id`, `customer_id`, `allocated_payment_id`; credit `credit_id`, `customer_id`, `invoice_id`, `consumed_by_payment_id`; email `email_id`, `customer_id`; gold `customer_id`, every entry of `invoice_ids` and `credit_ids`.
- Text fields are rewritten with one `pattern.sub`, replacing each match by its mapped value: every payment's `remittance_reference` and `bank_reference`; invoice `description`; credit `reason`; email `subject` and `body`; gold `rationale`.

One substitution pass per text. Never apply the mapping pair by pair: a new ID can equal another old ID.

### 6.3 `_finish(data, original, kind, index, operator, generator_seed)`

Sets `data["case_id"] = f"{original.seed_id}.{kind}.{index}"` and `data["variant"]` to the JSON dump of `Variant(kind=kind, index=index, parent_case_id=original.case_id, operator=operator, generator_seed=generator_seed)`, then returns `BenchCase.model_validate(data)`.

### 6.4 `resample(original, index, S)`

If `has_partial_mentions(original)`: return `None`. Otherwise `key = f"{S}:{original.seed_id}:resample:{index}"` and return `_finish(apply_rename(original, rename_map(original, key)), original, "resample", index, "resample_ids", S)`.

### 6.5 `_reorder(data, key)` and `noise_reorder(original, S)`

`_reorder` changes five lists of the dumped case in place, in this order of names and ID fields: `related_payments` by `payment_id`, `customers` by `customer_id`, `invoices` by `invoice_id`, `credits` by `credit_id`, `emails` by `email_id`. Each list is sorted by `hashlib.sha256(f"{key}:{name}:{record_id}".encode("utf-8")).hexdigest()`. If the list has more than one record and the sorted list equals the list before sorting, move its first record to the end. A reorder never returns the original order.

`noise_reorder`: dump the original, `_reorder(data, f"{S}:{original.seed_id}:noise:0")`, return `_finish(data, original, "noise", 0, "noise_reorder", S)`.

### 6.6 `noise_distractors(original, S)`

1. `key = f"{S}:{original.seed_id}:noise:1"`.
2. `customer_id = _target_customer(original)`: the gold customer for an `allocate` label, else the customer of the first invoice in case order. If the number of `eligible_invoices(original)` of that customer plus `DISTRACTOR_COUNT` is greater than `ORACLE_INVOICE_LIMIT`, return `None`: the ledger is already large, and the padded one could not be checked.
3. `own` = that customer's invoices, ascending invoice ID. `taken` = case-folded set of `record_ids(original)`.
4. `floor = minor_units(payment.amount) + sum of minor_units(c.amount) for c in eligible_credits(original)`.
5. For `number` in `range(DISTRACTOR_COUNT)` build an `Invoice` with:
   - `amount`: `Decimal(floor + 100 * (1 + draw(f"{key}:amount:{number}", 5000))) / 100`
   - `issue_date`: `payment.date - timedelta(days=1 + draw(f"{key}:date:{number}", 60))`
   - `due_date`: `issue_date + timedelta(days=30)`
   - `invoice_id`: `_new_invoice_id(own[0].invoice_id, taken, f"{key}:id:{number}")`
   - `description`: `own[draw(f"{key}:description:{number}", len(own))].description`
   - `customer_id`, and `currency = payment.currency`. Status stays the default `open`.
6. `padded` = the original with those eight invoices appended. If `valid_allocations(padded) != valid_allocations(original)` raise `ValueError(f"{original.case_id}: distractors changed the exact allocations")`.
7. Dump `padded`, `_reorder(data, key)`, return `_finish(data, original, "noise", 1, "noise_distractors", S)`.

`_new_invoice_id(template, taken, key)`: with `attempt` from 0: if the template has a digit, the candidate replaces each digit at `position` by `str(draw(f"{key}:{attempt}:{position}", 10))`; otherwise the candidate is `f"{template}-{draw(f'{key}:{attempt}', 9000) + 1000}"`. If the case-folded candidate is in `taken`, try the next attempt. Otherwise add it to `taken` and return it. Note the key layout differs from `rename_map`: here it is `key:attempt:position`.

Each added amount is at least one whole currency unit above the payment plus every eligible credit. That is why step 6 can never fail on a valid seed. It is checked anyway.

### 6.7 `twin_ambiguous(original, S)`

1. If the label is not `allocate`: return `None`.
2. `ids = record_ids(original)`; `pieces` = sorted set of all IDs and all their fragments. If `_token_pattern(pieces).search(original.payment.bank_reference)`: return `None`. A bank reference that names a record is an instruction the twin could not remove.
3. `key = f"{S}:{original.seed_id}:twin:0"`.
4. `stripped` = the original with `emails=[]` and the payment's `remittance_reference=""`.
5. If `len(valid_allocations(stripped)) >= 2`: operator `twin_no_remittance`, rationale `TWIN_RATIONALE_NO_REMITTANCE`.
6. Otherwise operator `twin_competitor`, rationale `TWIN_RATIONALE_COMPETITOR`, and:
   - `target = minor_units(payment.amount)`; `single` = the gold label has exactly one invoice and no credit.
   - If `single and target < 2`: return `None`.
   - `amounts = [target // 2, target - target // 2]` if `single`, else `[target]`.
   - `own` = the gold customer's invoices, ascending ID. `taken` = case-folded `ids`.
   - For each `(number, amount)` add a copy of `own[0]` with: `invoice_id = _new_invoice_id(own[0].invoice_id, taken, f"{key}:id:{number}")`, `amount = Decimal(amount) / 100`, `status = "open"`, `allocated_payment_id = None`, `issue_date = min(own[0].issue_date, payment.date)`.
   - Append them to `stripped`'s invoices. If fewer than 2 exact allocations exist now, raise `ValueError(f"{original.case_id}: the competitor did not create a second exact allocation")`.
7. Dump `stripped`; replace `gold` with the JSON dump of `Gold(decision="review", review_family="ambiguous_allocation", rationale=rationale)`; return `_finish(data, original, "twin", 0, operator, S)`.

Why two halves for a single-invoice label: one new invoice of the full amount would be a duplicate of the labelled one in everything but its ID. Two halves are a different shape.

### 6.8 `expand_seed(original, S)`

If `original.variant.kind != "original"` raise `ValueError(f"{original.case_id}: only an original case can be expanded")`. Otherwise return, in this order and dropping `None`: `resample` for index 0, 1, 2; `noise_reorder`; `noise_distractors`; `twin_ambiguous`.

### 6.9 `expand_tree(source, destination, S)`

1. `cases = load_cases(source)`.
2. If any case has a kind in `GENERATED_KINDS`, or is a `twin` with index 0, raise `ValueError(f"{case.case_id}: this kind and index are reserved for generated variants")`. Nothing is written.
3. `output` = all loaded cases, plus `expand_seed(case, S)` for every original. Count the generated variants per operator.
4. `issues = validate_cases(output)`. If any: raise `ValueError(f"expansion produced {len(issues)} validation issues; first: {first.case_id} {first.code}")`. Nothing is written.
5. Write every case, in ascending case ID, with `write_case` to `destination / case.seed_id / f"{case.variant.kind}.{case.variant.index}.json"`.
6. Return `(len(cases), len(output), counts)`.

Human-written variants in the source (paraphrases, twins with index 1 or more) are passed through unchanged.

## 9. Edge cases and error handling

| Case | Required behaviour |
| --- | --- |
| A message writes `0412` for invoice `HF/26-27/0412` | `has_partial_mentions` is true; no `resample` variants for this seed; the other variants are produced |
| A message contains `10412` and the full ID | Not a partial mention. `10412` is a different token. |
| An ID with no digit, for example `C-HARBOUR` | Never renamed |
| The hash order of a list equals its current order | Rotated by one |
| A review seed | No generated twin |
| The target customer has more than 16 eligible invoices | No `noise_distractors` variant |
| An allocate seed whose bank reference contains a record ID or a fragment of one | No generated twin |
| A source directory that already contains a `noise`, a `resample` or a `twin.0` case | `ValueError`, nothing written |
| A short ID such as `CN-88` mentioned as `88` | Not detected: `88` is shorter than three characters. The guide requires IDs of at least four characters and one full mention, which reduces this. It is a stated limit. The owner checks resampled variants of seeds with short IDs by reading them. |
