## 1. Objective and rationale

Make `process_payment` build the `ProofSet`, run `search` once, send the payment to human review when the search is `unknown`, and give the rules-only matcher the proof bundle and the search's alternatives.

Why: finding F3, rules-only half. With ten open invoices where one equals the payment and two cap-dropped invoices also sum to it, the pipeline returns `matched_normally` today. No model is involved. After this task the matcher sees both allocations and declines.

This task leaves the proposal path (everything after the investigator call) on the prompt bundle. RP-104 moves it.

## 6. Input and output contracts

### 6.1 `baseline_match`

When `alternatives` is `None`, behaviour is exactly today's. When a list is given, the function uses it in place of `find_valid_alternatives(bundle)` and does not enumerate. Nothing else in the function changes.

### 6.2 `process_payment`, in order

1. `proof_set = build_proof_set(payment, dataset)`; `candidates = proof_set.prompt_bundle`.
2. Replay gate: unchanged, including its `candidates=_candidate_dump(candidates)`.
3. `outcome = search(proof_set)`.
4. If `outcome.status == STATUS_UNKNOWN`, return a `ProcessingResult` with:
   - `baseline = BaselineResult(payment_id=..., status="unresolved", reason="search_incomplete")`
   - `decision = Decision(payment_id=..., decision="human_review", proof={"search_status": outcome.status, "search_detail": outcome.detail, "incomplete_reasons": list(outcome.incomplete_reasons), "investigator_skipped": True}, reason="search_incomplete", latency_ms=...)`
   - `payment=payment.model_dump(mode="json")`, `candidates=_candidate_dump(candidates)` (the prompt bundle)
   - no other field set. The investigator is not called.
5. `proof_bundle = proof_set.proof_bundle`; `baseline = baseline_match(proof_bundle, alternatives=list(outcome.alternatives))`.
6. Matched return: unchanged except `candidates=_candidate_dump(proof_bundle)`.
7. Everything from the status gate (`backend/app/services/pipeline.py:104`) to the end: unchanged in this task. It keeps using `candidates`.

`latency_ms` in step 4 is computed the same way as in the replay gate.

## 9. Edge cases and error handling

| Case | Required behaviour |
| --- | --- |
| Replayed payment whose ledger is also over the search limit | The replay gate answers. Reason `duplicate_bank_transaction`. |
| Search is `none` or `ambiguous` | Not an early return. The matcher runs and declines for its own reasons, as today. |
| Search is `unique` | The matcher runs. It may still decline (payer identity, contradictions). The search status alone never authorizes anything. |
| `build_proof_set` or `search` raises | Not caught |
